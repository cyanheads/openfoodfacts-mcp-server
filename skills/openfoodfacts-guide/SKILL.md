## Scope

Packaged, barcoded foods as Open Food Facts contributors recorded them: label text, declared allergens and traces, additives, Open Food Facts' computed grades and nutrient levels, and nutrition per 100 g (per 100 ml for liquids) and per serving. It is not a verdict on whether a food is safe for a particular person, and it holds no recalls. Reference composition for generic, unbranded foods belongs to a food-composition database such as USDA FoodData Central.

## Identifiers

| Identifier | Where it comes from |
|:--|:--|
| Barcode | The user (a scan or the pack), or the rows of off_search_products. One product has many barcodes — sizes, regional editions, reformulations — and each is a separate record with its own completeness and grades. |
| Tag ID (`en:organic`, `en:nuts`) | off_browse_taxonomy, or the tag arrays on a product record. The same ID can mean different things in different facets: the category `en:nuts` holds peanut products, while the allergen `en:nuts` means tree nuts. |
| Category tags | A record carries its category's ancestors too (a pistachio row lists `en:snacks`, `en:salty-snacks`, `en:nuts`, `en:pistachios`), so a broad category filter also matches products filed under its subcategories. |
| Ingredient tags (`en:oat`, `en:inulin`) | off_browse_taxonomy with facet `ingredients` and a search term; it has no reference list, so a call without a term returns nothing. IDs are singular: `oat` finds `en:oat`, `oats` finds nothing. A product record lists them as `ingredients[].id`. off_search_products filters on them with `ingredients_tag` (an array requires all of its values, and a parent matches its descendants: `en:vegetable` matches carrot). That filter reads the text index, which lags the live database, with or without `query`; for a vegan or palm-oil verdict use `ingredients_analysis_tag` instead. |
| Off-taxonomy entries | A product's tag arrays can hold contributor entries the taxonomy never canonicalized: a non-`en:` prefix or display text with capitals, spaces, or accents (`fr:Goûter`, `en:Pâtes à tartiner`). Don't reuse one as a filter value; resolve the concept with off_browse_taxonomy first. |

## Gates

1. **Allergy questions: never answer "safe" or "free of X".** Report what the record says and how far it goes. Read all three sources: `ingredients_text` (in the record's main language, named by `lang`, often with allergens emphasized in capitals or brackets), `allergens_tags`, and `traces_tags`. An empty `traces_tags` means no trace data was entered, not that the label carries no warning. When the main-language text is short or disagrees with the allergen tags, read `ingredients_text_languages` for the text entered in other languages and open the `image_ingredients_url` photo: the main-language text can be a contributor's translation rather than what the pack prints. When the sources still disagree, say the record is unreliable: a record can carry a truncated ingredients text beside allergen tags that text cannot support. End by pointing the user to the physical label.
2. **Nut allergies need two tags.** `en:nuts` means tree nuts; peanuts are the separate `en:peanuts`. Check both on the record, and pass both to exclude_allergens or exclude_traces.
3. **Free-from searches start from a positive claim.** An exclusion alone also passes every product with no allergen data entered, so select first on something the record asserts: a label (`en:no-gluten`, `en:vegan`) or a free-from category (`en:gluten-free-pasta`). Add the exclusion on top, then confirm shortlisted barcodes with off_get_product. For vegan, the ingredients-analysis verdict `en:vegan` is Open Food Facts' computation from the parsed ingredients, while the label `en:vegan` is a claim printed on the pack. They are different evidence, so say which one you used.
4. **Grade ranges are one call, one array.** nutrition_grade, nova_group, and ecoscore_grade (Green-Score) each take one grade or an array matching any of them, never all of them: a product carries one grade. "Nutri-Score B or better" is `["a", "b"]`. Green-Score `a` excludes `a-plus`, so A or better is `["a-plus", "a"]`. A product with no grade drops out. A tag-only Green-Score search matches the grade Open Food Facts files for France, while each row shows the world grade, so a row's letter can differ from the one it matched.
5. **A product named without a barcode: pick a barcode deliberately.** Don't take the first search row on faith. Records for one product can carry different Nutri-Score and NOVA grades even when their nutrition is identical, when one record's ingredient list or other entered data is incomplete. Prefer the user's own barcode. Otherwise sort by unique_scans_n, favor high `completeness` (each row carries it, and it can exceed 1), tell pack sizes and editions apart by `quantity`, and name the barcode the answer came from.
6. **Grades and nutrient levels are Open Food Facts' computation from the record**, not the grade printed on the pack. When a user quotes a different grade, the record's data is the first suspect: check its `completeness`, `data_quality_tags`, and ingredient list. `nutrient_levels` (fat, saturated fat, sugars, salt as low, moderate, or high) is its verdict against fixed thresholds, halved for beverages, and `basis` says which figures it judged. On `prepared` it judged the prepared figures, so it can disagree with the as-sold figures `nutriments` fills from the stored set; say which basis you quote. `nutriscore_score` is the points behind the Nutri-Score grade (lower is better) and ranks products of one kind only: beverages, and fats, oils, nuts, and seeds, are graded on their own thresholds, so the same points carry different grades across kinds. `ecoscore_score` is the world score behind the Green-Score grade (higher is better).
7. **Spend searches one at a time.** The search budget is about 10 upstream requests a minute on the default configuration. The server process holds it, so every caller of a shared deployment draws from it, and each retry of a failing request spends its own slot. Never fan out parallel searches; when the budget runs out, the error's `data.retryAfter` gives the wait in seconds, as does `retryAfter` on each off_compare_products `failed` entry a budget or rate limit refused. Product lookups draw on a separate budget of about 15 a minute. off_compare_products spends one lookup from it per barcode, and off_get_product one, but a barcode whose read returned only prepared figures takes a second lookup for its stored as-sold set, so a compare can spend up to twice the barcodes. The limiter refuses rather than waits: a 10-barcode compare reads at most 5 stored sets from a fresh minute, and the rest come back `unread` with reason `rate_limited`. A barcode served from the local mirror (`source` `off_mirror`) spends neither lookup, and the stored set comes from the same record.

## Workflows

**Allergy or diet check on one product.** Call off_get_product, with `fields` narrowed to the ingredients, allergen, trace, and analysis fields when nutrition doesn't matter. Apply gates 1 and 2. If the user named a product rather than a barcode, apply gate 5 first.

**Find products matching a diet and a nutrition target.** Resolve each human term (category, label, allergen, country) with off_browse_taxonomy. Express the diet as a positive claim (gate 3), the grade as one array (gate 4), and the nutrition target as nutrient_filters. Nutrient filters move the search to the text index, which lags the live database, and each row then carries the index values the filters were compared against; a grade filter on that path matches the grades the index holds, which each row shows and which can differ from the current record. Each bound is compared as given, decimals included (`sugars` above 3.5 excludes 3.5), and a nutrient filter reaches only records whose text-index entry carries that nutrient, so a product that meets the target can be missing and an empty result does not show that none exists. Confirm the shortlist with off_get_product before presenting it. The answer's `text_index_as_of` dates the index by its newest record, so a product contributed since is missing and one edited since is matched as it was then; row times (`last_modified`, `created`) are the indexed revision's.

**Compare products.** off_compare_products returns nutrition and grades only: no ingredients, allergens, or additives. Each Nutri-Score and Green-Score shows its points beside the grade (`b (1)`); Nutri-Score points break a grade tie only between products of one kind. The two carbohydrate columns are different nutrients: `carbohydrates_100g` is Open Food Facts' carbohydrates figure, which records entered from US labels often fill with the label's total, and `carbohydrates_total_100g` is the separate total including fiber. Quote each as its own column and never subtract fiber from one to get the other. A row from the local mirror that predates the score points names them in `mirror_fields_unread`: they were not read, so read the barcode with off_get_product rather than treating them as absent. Open Food Facts returns one preparation state of the nutrition per read: figures for the prepared product arrive in a row's `prepared` object. A row whose read returned only prepared figures gets one more read of the as-sold set its record stores, after every barcode's product read has settled, and `stored_as_sold` says how it went: `read` fills the as-sold columns from that one set, `none` means the record stores no usable set, and `unread` (with a `reason`) means it could not be read, so as-sold figures absent beside `prepared` then mean the read failed, not that the record holds none. Don't compare an as-sold figure with a prepared one. Stored sets pass through as filed: a powder whose as-sold energy is below its prepared energy has its sets swapped on the record (`3664346306027` files 148 kcal as sold and 355 prepared), so the figures are served as stored. For additives or allergens, follow up per barcode with off_get_product, narrowing `fields` to `additives_tags`, `allergens_tags`, and `ingredients_text`. Mind the shared product budget when the list is long (gate 7). Don't count additives by array length: `additives_tags` can list a parent and a specific form of the same additive (`en:e322` lecithins and `en:e322i` soya lecithin on one record). off_browse_taxonomy with facet `additives` and the E-number gives the additive's name.

**Reading where a result came from.** Product, compare, and search results carry `source`. `off_api` is Open Food Facts itself. `off_mirror` is this server's local copy of the export: it reflects contributor edits through `mirror_as_of`, so a product contributed or edited since is missing or shown as it was, and its computed values (grades, nutrient levels, ingredient analysis, additives, allergens and traces, completeness, data-quality tags) are current only as of the record's last edit or the copy's last full reload, about every 30 days, and a product removed since that reload can still be shown (the `mirror_snapshot` note says so); say as of when you report it, and that a grade or allergen verdict from the copy can lag the live record. An off_get_product answer carrying `mirror_fields_unread` lacks the fields it names because they were not read, so never report them as absent from the record. A tag-only search the mirror serves has an exact `total` and reaches its first 10,000 results, while one read live stops at page 10; either fails as `page_out_of_range` past its bound, so narrow the filters rather than paging. Under the default order, `popularity_key`, and `unique_scans_n`, the mirror sorts by the values stored with each record, while a live search ranks by its current scan counts, so the orders can differ; do not treat the two as the same ranking. A tag-only search is served by the mirror only when every tag value is confirmed (IDs from off_browse_taxonomy, and a brand the mirror holds products under), so an unrecognized value falls back to the live backend. `brands_tag` takes a brand name or slug, slugged the way Open Food Facts slugs it (`Nestlé` → `nestle`), and matches every other name its Open Food Facts brand entry lists (`7-Up`, `7up`, and `Seven Up` count the same products) on every path, so put brand wording there, never in `query`; for a brand the mirror holds nothing under, a page past 10 is answered empty or refused with the live total rather than paged. A search carrying `ecoscore_grade` or `brands_tag` also reads live until the mirror has completed a reload that indexes Green-Score or keys brands, so it stops at page 10 until then.

**A tag-only search fails with upstream_error.** Searches by tag filters alone and searches carrying a query read separate backends, so one can fail while the other answers. Add a query word the product's name would carry (`pasta` with `categories_tag` `en:pastas`) to reroute the same filters to the text index. Query words match product names only, so category, label, and brand wording stays in the tag filters, and additives_tag combines with a query. The text index lags the live database, so say so, with the `text_index_as_of` date when the answer carries one, when you report results that came through it.
