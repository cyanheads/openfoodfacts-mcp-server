# openfoodfacts-mcp-server — Design

## MCP Surface

### Tools

| Name | Description | Key Inputs | Annotations |
|:-----|:------------|:-----------|:------------|
| `off_get_product` | Fetch a product by barcode (4–40 digits). Returns name, generic name, brands, quantity, ingredients (raw text + parsed list), declared and trace allergens, additives, ingredient analysis, Nutri-Score, NOVA group, Green-Score (each grade with its points), nutrient levels, nutriments (per serving, and per 100 g, or per 100 ml for liquids), categories, labels, packaging, origins, countries of sale, image and label-photo URLs, completeness signal, and last-modified and created times. Missing fields mean "not yet entered in the database" — not that the attribute is absent from the real product — except that a product read returning only prepared nutrition is followed by a read of the as-sold set the record stores, which fills the as-sold fields and is reported as `nutriments.stored_as_sold`. | `barcode` (string, required), `fields` (optional field subset) | `readOnlyHint: true` |
| `off_search_products` | Search by keyword, structured tag filters, and/or numeric nutrient thresholds (per 100 g, or per 100 ml for liquids). Returns summary rows with barcodes for follow-up lookups. Use when the barcode is unknown or to explore a category. Filters use canonical tag IDs (e.g. `en:organic`, `en:no-gluten`) — use `off_browse_taxonomy` to resolve human terms to tag IDs. | `query` (text search), `categories_tag`, `brands_tag`, `labels_tag` (string or array), `allergens_tag`, `traces_tag`, `exclude_allergens`, `exclude_traces`, `ingredients_analysis_tag`, `ingredients_tag` (string or array), `additives_tag`, `nutrient_filters`, `nutrition_grade`, `nova_group`, `ecoscore_grade` (each a grade or an array matching any), `countries_tag`, `sort_by`, `page`, `page_size` | `readOnlyHint: true` |
| `off_compare_products` | Side-by-side nutrition and scoring comparison for up to 10 distinct barcodes per call; more are listed in `unprocessed`, unfetched. Returns a normalized table of calories, fat, saturated fat, carbohydrates, total carbohydrates including fiber, sugars, salt, protein, and fiber (per 100 g, or per 100 ml for liquids), plus Nutri-Score and Green-Score (each with its points) and NOVA; figures for the prepared product arrive in a separate `prepared` object and table, and a row whose read returned only prepared figures gets the stored as-sold read, reported as `stored_as_sold`. Designed for "which of these cereals is healthiest?" workflows. | `barcodes` (array of 2–100 barcode strings, 4–40 digits each) | `readOnlyHint: true` |
| `off_browse_taxonomy` | Resolve a human term to the canonical tag ID for a filter facet: categories, labels, allergens, additives, countries, ingredients, nova groups, nutrition grades. A search term resolves against the live Open Food Facts taxonomy, merged behind an in-process sample (ingredients has none and resolves only live); omitting it lists that sample, which is all the upstream suggester can support, and lists nothing for ingredients. Use before `off_search_products` to build precise filter values. | `facet` (enum), `search` (optional term), `limit` | `readOnlyHint: true`, `openWorldHint: true` |

### Resources

None. All data is reachable via tools. The barcode-keyed product data has a natural URI shape but tool-only clients are the primary target.

### Prompts

None. The server is data-oriented; no recurring analysis templates warrant a prompt definition.

## Overview

Wraps the [Open Food Facts API v2](https://world.openfoodfacts.org/) — a free, keyless, crowd-sourced global food product database covering 3M+ products. The primary access pattern is barcode → full product label (ingredients, allergens, scores, nutrition). Complements `usda-mcp-server` (US FoodData Central: generic, US-centric foods). Open Food Facts is the global, barcode-addressable, branded-product side.

Target audience: diet and allergen tracking, grocery and meal-planning tools, health-conscious shoppers, agents turning a barcode or product name into structured nutrition and ingredient data.

Attribution: data under [ODbL 1.0](https://opendatacommons.org/licenses/odbl/1.0/) — cite Open Food Facts in downstream use.

---

## Requirements

- No API key. Mandatory identifying `User-Agent` header: `openfoodfacts-mcp-server/<version> (casey@caseyjhand.com)` — baked into the service layer, not per-call.
- Read-only — no write-back of product edits.
- Per-endpoint rate limits: product reads ~15/min, search ~10/min, taxonomy resolution ~10/min. Rate limiting enforced in service layer, one token bucket per class, counted in upstream HTTP requests rather than tool calls — the slot is charged per attempt inside the retry boundary, so a retried request spends its own. The product and search figures are the per-IP ceilings Open Food Facts publishes; exceeding them is answered with an IP ban rather than a throttle, so the defaults sit at the published number and go lower — never higher — on a shared outbound IP.
- Field selection mandatory on every request — the product object is ~200 keys; always scope `fields=`.
- Tag vocabulary, not free text — search filters use canonical tag IDs (`en:organic`, `en:no-gluten`).
- Missing fields signal incomplete crowd-sourced data, not product attribute absence — surface this distinction explicitly in tool descriptions and output. The exception is nutrition read in a prepared state, which omits as-sold figures the record can still hold; the stored as-sold read supplies them, and where that read could not run, the output says what the read returned, never that the record lacks them.
- Computed scores (Nutri-Score, NOVA, Green-Score) carry regional formula and missing-data caveats — return grade letters as-is, never infer absolute health claims.
- Data is under ODbL; tool descriptions note attribution requirement.

## Confirmed API Shapes (live-probed 2026-05-30)

### Product lookup (`/api/v2/product/{barcode}.json`)

**Hit:** `GET /api/v2/product/3017620422003.json?fields=product_name,brands,nutriscore_grade,nutriments`

```json
{
  "code": "3017620422003",
  "status": 1,
  "status_verbose": "product found",
  "product": {
    "brands": "Nutella",
    "nutriscore_grade": "e",
    "product_name": "Nutella",
    "nutriments": {
      "energy-kcal": 539,
      "energy-kcal_100g": 539,
      "energy-kcal_unit": "kcal",
      "energy-kcal_value": 539,
      "fat": 30.9,
      "fat_100g": 30.9,
      "fat_unit": "g",
      "sugars": 56.3,
      "sugars_100g": 56.3,
      "salt_100g": 0.107,
      "proteins_100g": 6.3,
      "nova-group": 4,
      "nova-group_100g": 4
    }
  }
}
```

**Nutriments shape:** flat key-value map. Each nutrient has up to six variants: `{key}`, `{key}_100g`, `{key}_unit`, `{key}_value`, `{key}_serving` (when serving data present), `{key}_modifier` (e.g. `~` for approximate). The `_100g` variant is the normalized figure per 100 g, or per 100 ml for liquids, and `_unit` is, on legacy records, the unit the contributor entered rather than the unit `_100g` and `_serving` are in. Keys use hyphens: `energy-kcal`, `saturated-fat`, `added-sugars`.

**Fields confirmed in full product object:** `product_name`, `generic_name` (the main-language value, which is `""` when none is entered there even if a language variant holds text — live 2026-11-08, 4000417025005), `brands`, `quantity`, `ingredients_text`, `allergens_tags` (array, `en:milk` format), `traces_tags` (array, same format — `["en:none"]` declares no traces, `[]` is not-yet-entered), `additives_tags` (array, `en:e322` format), `ingredients_analysis_tags` (array, `en:vegan` / `en:maybe-vegan` / `en:palm-oil-free` format), `nutriscore_grade` (`a`–`e`, `unknown`, `not-applicable`, or absent), `nova_group` (1–4 integer or absent), `ecoscore_grade` (the Green-Score scale `a-plus`, `a`–`f`, plus `unknown` and `not-applicable` — seen live: `not-applicable` on 5449000000996, `f` on 5034660516170), `nutrient_levels` (object of `low` / `moderate` / `high` under `fat`, `saturated-fat`, `sugars`, and `salt`, computed on the record's aggregated nutrition set, where prepared figures win; `{}` when none was computed and a key missing for a nutrient with no figure; thresholds halve for `en:beverages` — live 2026-11-08: 3664346306027 on its prepared figures, 0000460938714 with `fat` alone), `categories_tags` (array), `labels_tags` (array), `packaging_tags` (array), `origins_tags` (array, often empty), `countries_tags` (array, the values `off_search_products` filters on as `countries_tag`), `image_url`, `completeness` (a float that can exceed 1, e.g. 1.0875), `data_quality_tags` (crowd-sourced QA flags), and also `lang` (the main language code), `ingredients_text_languages` (the ingredients text per language code the record lists, empty entries included, which the tool leaves out), `nutriscore_score` and `ecoscore_score` (the points behind the grades), `image_ingredients_url` and `image_nutrition_url` (the selected label photos, English first, then the main language, then the first code), and `last_modified_t` and `created_t` (epoch seconds).

**Field subsets are expanded to their dependencies.** The API returns exactly the `fields=` list it is given, so `off_get_product` adds what a requested field needs to be readable before sending: `nutriments` brings `serving_size`, `serving_quantity`, and `serving_quantity_unit` — the combined request is honored, verified on barcode 0028400157827 — `nutrient_levels` brings `nutriments` and those three, since the figures `nutriments` holds decide the levels' `basis`, and `serving_quantity` and `serving_quantity_unit` each bring the other plus `serving_size`, while `serving_size` expands to nothing (see "The serving fields expand as a closed group"); `ingredients_text` and `ingredients_text_languages` each bring `lang`, which names the language the text is in or keyed against; `nutriscore_score` and `ecoscore_score` each bring their grade, since points read without it render beside `N/A` for a grade the record may hold. `requested_fields` echoes the expanded set, so a field present in `product` is always one the response says it asked for and the "not requested" wording can never contradict the payload.

**Missing barcode response (status:0):** HTTP 404 with `{"code":"2961836540127","status":0,"status_verbose":"product not found"}` (live 2026-10-13). An HTTP 200 carrying `status: 0` (`"no code or invalid code"`, live 2026-10-13 for `00000636`) is the same answer and is still read as not found.

**A 2xx body is a product answer only in one of two shapes:** `status: 0`, or `status: 1` with a `product` object. A field subset none of whose fields is entered comes back as `"product": {}` with `status: 1` (live 2026-10-13, `fields=zz_no_such_field`) — a found product with nothing recorded, not a miss. Any other 2xx body (`{}`, `{"status":1}` with no product, a non-numeric `status`) is a malformed envelope and raises the retryable `upstream_error`; read as an answer, it would turn a broken response into a confident "not found".

### Search (`/api/v2/search`)

**Hit:** `GET /api/v2/search?categories_tags_en=breakfast-cereals&fields=code,product_name,nutriscore_grade&page_size=5`

```json
{
  "count": 25894,
  "page": 1,
  "page_count": 5,
  "page_size": 5,
  "skip": 0,
  "products": [...]
}
```

**Pagination:** uses `page` (1-based) and `page_size` params. Response includes `count` (total matching products), `page_count` (number of products returned on this page — mirrors `page_size` for full pages, less for the last page), `skip` (row offset). **There is no total-pages field** — compute it as `Math.ceil(count / page_size)` in the service layer if needed. **Page 10 is the deepest page served to a client that is not logged in**: `search_and_display_products` in Product Opener's `lib/ProductOpener/Display.pm` answers any `page > 10` with HTTP 401 and a rendered `robots_not_served_here` page before it runs the query. The bound is on the page number, not on results — live 2026-09-23, page 11 was refused at `page_size` 1 and on a brand filter matching nothing, while page 10 at `page_size` 50 was served. A tag-only search the local mirror serves has no such bound (see "Local export mirror").

**`count` is present only when the query ran.** `search_and_display_products` starts its response as `{page, page_size, skip, products: []}` and adds `count` and `page_count` only after the MongoDB query succeeds; a failed query is logged and that skeleton answered with HTTP 200, and a failed count query can leave `count: null`. A zero-match answer carries `count: 0` (live 2026-10-13). So the service accepts a body only with a `products` list and a numeric `count`, and raises anything else as the retryable `upstream_error` rather than reporting zero matches.

**Filter params confirmed working:**
- `categories_tags_en=breakfast-cereals` — English label (no `en:` prefix needed for `_en` params)
- `brands_tags=nutella` — brand slug
- `nutrition_grades_tags=e` — single letter a–e (the bare `nutrition_grades` key is silently ignored); `nova_groups_tags=4` and `environmental_score_tags=a-plus` (the Green-Score grades `a-plus`, `a`–`f`, as Product Opener computes them for France; `ecoscore_tags` is a transition copy) work the same way. A `|`-separated value is any of its entries (`nutrition_grades_tags=a|b`), so several grades of one input travel as one parameter
- Multiple filters compose as AND

**Tag filter params in search:** `categories_tags`, `labels_tags`, `allergens_tags`, `traces_tags`, `ingredients_analysis_tags`, `additives_tags`, `brands_tags`, `countries_tags` — use canonical `en:X` format. Any `*_tags` value is a comma-separated AND list in which a `-` prefix negates (`add_params_to_query` in `Display.pm`), and every value, negated ones included, is canonicalized. Live 2026-09-22/23 on `en:chocolates` (32,687): `allergens_tags=en:nuts` 6,603 and `-en:nuts` 26,084 (15,936 of those with no allergen data at all, `allergens_tags=unknown`); `allergens_tags=en:nuts,-en:milk` 1,302; `traces_tags=en:nuts` 12,450 (so is `en:nut`, canonicalized through the allergen taxonomy), `-en:nuts` 20,237, `en:nuts,-en:milk` 8,222; `ingredients_analysis_tags=en:vegan` 2,553; `labels_tags=en:organic,en:fair-trade` 2,183 against 4,653 and 3,989 alone. The `_en` suffix variants accept plain English slugs. Tag values match exactly against the normalized slug: `brands_tags=nutella` matches while `brands_tags=nutell` returns zero on this endpoint, and `brands:"xx:nutell"` matches nothing on the text backend alike.

### Text search (`https://search.openfoodfacts.org/search`)

Separate backend (search-a-licious 2.x over Elasticsearch, whose Open Food Facts schema is `data/config/openfoodfacts.yml`), reached whenever a request carries free text, a nutrient constraint, or an ingredient filter. The service calls it as `POST /search` with the parameters in a JSON body — `{q, langs, fields, page, page_size, sort_by?}`, the same parameters the GET form takes (live-verified identical for `sort_by`, `page`, `page_size`, and `fields`). It refuses a field its schema does not hold with HTTP 400, so every field name below is 2.x's. Its envelope differs from `/api/v2/search` in three ways that the service normalizes or surfaces:

```json
{
  "count": 10000,
  "is_count_exact": false,
  "page": 1,
  "page_size": 2,
  "page_count": 5000,
  "hits": []
}
```

- **`count` is a floor, not a total, when `is_count_exact` is false.** The backend stops counting hits at 10,000 and reports which side of that it landed on. Live-probed: `chocolate`, `water`, `milk` all report `count: 10000, is_count_exact: false`; `kombucha` reports `count: 3464, is_count_exact: true`. `/api/v2/search` has no such ceiling — the same `en:beverages` filter that clips to 10,000 here counts 230,860 there. `is_count_exact` is a required property of the endpoint's documented success schema, so it is read directly rather than inferred by comparing `count` to a local constant.
- **A success envelope must carry `hits`, a numeric `count`, and a boolean `is_count_exact`.** search-a-licious's `SuccessSearchResponse` requires all three, and every live answer carries them, zero-hit pages included (`count: 0, hits: [], is_count_exact: true`). A 2xx body without them, and not the `errors` envelope below, is malformed: the service raises it as the retryable `upstream_error` instead of defaulting to zero matches and an exact count.
- **`page_count` means total pages**, not products on this page. Normalized to products-on-page in the service so both paths return one shape.
- **The index lags the live database.** Live 2026-11-24 its newest record was last modified 2026-11-24T05:33:34Z and was unchanged from 19:46Z to 19:58Z, so a product contributed after the newest record is absent and one edited since is matched as it was then, while a tag-only search reads the live database, or the local mirror when one serves it. `/health` reports Redis and Elasticsearch connectivity only, publishing no index timestamp, so the service dates the index itself: a `POST /search` with no `q`, `sort_by: "-last_modified_t"`, `page_size: 1`, and `fields: ["last_modified_t"]` returns the newest record the index holds (omitting `q` matches the whole index, while `q=*` matches nothing). Live 2026-11-24 the probe answered in 0.5–0.7 s, beside text searches that took 0.6–0.7 s. The date reaches the caller as `text_index_as_of`, and the tool states the property in an enrichment field on every response this backend answered.
- **Nutrient values are queryable here and nowhere else.** `nutriments.<name>_100g` accepts Lucene range clauses: square brackets are inclusive (`[* TO 2]` → `lte`), curly braces exclusive (`{* TO 2}` → `lt`), `*` is an open bound, and hyphenated names need no escaping. The `nutriments.` prefix is mandatory. Nine fields are indexed per 100 g, or per 100 ml for liquids (`energy-kcal`, `fat`, `saturated-fat`, `carbohydrates`, `sugars`, `fiber`, `proteins`, `salt`, `sodium`), and 2.x maps all of them as `float`, so a bound compares as the decimal it is (live 2026-11-24: `energy-kcal_100g:{54 TO 55}` matched 1,312 records at 54.2 to 54.8). The index maps no per-serving field, so only the per-100 basis is offered. `/api/v2/search` documents the same comparisons (`docs/api/ref/api.yaml`, "Conditions on nutriments") but ignores them: `sugars_100g<2`, `>9999`, and `<0.0001` each returned the identical unfiltered `count: 4554`, percent-encoded and raw alike.
- **A constraint reaches only records whose indexed entry carries the nutrient.** Many indexed records hold no `nutriments` map at all, including records whose live read carries nutrition figures: live 2026-11-24 the index holds nutrient values for 47 of 1,447 `en:skyrs` records and 671 of 5,026 `en:ketchup` records. A product that meets a constraint on the live record can therefore be missing from the results, and an empty result does not show that none exists. `sort_by` on a nutrient is not offered.
- **The values a nutrient filter matched come back from the same request.** A constrained search adds `nutriments` to `fields`, and each hit that has one carries the index's own per-100 map (live 2026-10-13: ten keys at most, `energy-kj_100g` beside the nine filterable ones, every value a JSON number); the service keeps only the constrained keys as `indexed_nutriments`, keyed as `off_get_product` keys them (`sugars_100g`, `energy_kcal_100g`), and leaves a nutrient the index holds no value for out. The whole map is requested. The index's values can differ from the live record's: `dark chocolate` with sugars below 8 matched `7771711000483` on an indexed 3.85 g, which `off_get_product` reports as 17.5 g. Cost, measured on that search: +3.7 KB on a 20-row page (24.5 → 28.2 KB) and +9.1 KB on a 50-row page (33.7 → 42.8 KB), no added latency and no extra request. A search with no nutrient filter sends the summary field list unchanged.
- **Tag facets drop the `_tags` suffix, except two.** The 2.x index holds `categories`, `labels`, `countries`, `allergens`, `traces`, `additives`, and `brands` as tag IDs, while `ingredients_tags` and `ingredients_analysis_tags` keep their names. `additives:"en:e330"` and its exclusion partition the `en:hummus` records exactly (live 2026-11-24), so an additive filter combines with a query, nutrient constraints, and an ingredient filter like any other tag filter.
- **Grades are single-valued fields, and several are an OR group.** `nutriscore_grade`, `nova_group`, and `environmental_score_grade` hold one grade per product, so `nutriscore_grade:(a OR b)` counts the products graded either, the sum of the two single-grade counts (live 2026-11-08, `en:breakfast-cereals` sold in France: 1,599 for `a`, 746 for `b`, 2,345 for the group). A grade carrying punctuation is quoted (`environmental_score_grade:("a-plus" OR a)`). Green-Score filters on `environmental_score_grade`, the grade each row shows as `ecoscore_grade`. The grades lag the live records as the product set does.
- **Tag fields match exactly, with no canonicalization.** `categories`, `labels`, `countries`, `allergens`, `traces`, `additives`, `brands`, and `ingredients_tags` (which holds each parsed ingredient's taxonomy parents too) are exact-match keyword fields, so the value must be the stored ID byte for byte. `/api/v2/search` canonicalizes the same parameters (case, synonyms, plurals, a missing language prefix) and the text backend does not. The tool therefore canonicalizes every taxonomy tag value before it reaches this backend, and sends a brand under every ID the index can hold it under (next bullet).
- **A brand is stored under several spellings.** The index holds `brands` as tag IDs: a taxonomy brand under its `xx:` ID, an off-taxonomy brand under its slug and under the spellings contributors typed (`xx:member-s-mark`, `xx:Member's Mark`), and a record last indexed before Product Opener wrote the prefix under the bare slug. Live 2026-11-24 Heinz is stored as `xx:heinz` (3,157 products) and bare `heinz` (523), and Όλυμπος under bare `όλυμπος` (10 products) and none under `όλυμποσ`, with 36 under `xx:ΌΛΥΜΠΟΣ` or `xx:Όλυμπος`. A text search therefore sends one any-of group of `xx:<the brand as given>` and each of the brand's keys (`brandKeys`) bare and `xx:`-prefixed, plus the final-`ς` spelling of a key ending in `σ`.
- **Exclusions are negated clauses, and a wrong value excludes nothing.** A top-level `-field:"value"` excludes, and a second clause on one field is a second term that must also hold: live 2026-11-24 `allergens:"en:sesame-seeds"` and its exclusion partition the `en:hummus` products exactly. A value the field does not hold excludes nothing: it is a no-op, not a zero. Inclusions degrade toward an honest empty result; an exclusion degrades toward a result that looks filtered and is not.
- **Free text matches only the languages it is sent, in names.** 2.x searches `product_name.<lang>` and `generic_name.<lang>` only for the languages named in `langs`, English alone by default (`шоколад` 359 hits, against 870 with the first 30; `confiture abricot` 805, against 10,000+), so a product named only in French, Russian, or Portuguese is invisible to a query that sends none. The index holds name fields for 181 languages plus `main`, the name in the product's own main language, whatever that is (live 2026-11-24: `czekolada` 108 on the 31 codes, 370 with `main` added). The service sends 31 codes (`en fr it es de nl ar hy eu bn bg ca da et fi gl el hi hu id ga lv lt fa pt ro ru sv tr th no`) and `main`: each code costs two fields per query word, so the other 150 stay unsent, and the list is a constant, not a caller input.
- **Query words reach names only.** The category, label, and brand fields 2.x also searches hold tag IDs no word equals (live 2026-11-24: `hummus` matched 2,643 of the 4,616 `en:hummus` products; Heinz `50457250` matched none of `heinz`, `sauces`, `vegan`), so a category, label, or brand reaches a search through its tag filter.
- **Every bare word is required, and a stop word is not.** 2.x requires each space-separated bare word, and its analyzers leave stop words out of that requirement (live 2026-11-24: `confiture de fraise` and `confiture fraise` both 1,956). A word joined to another by punctuation is one term to it, matched by any one of the parts its analyzers split it into (`coca-cola` 10,000+ against `coca cola` 2,969), so the service sends the words apart. A word is a run of letters, marks, digits, and `_`, continuing across a single `'`, `’`, or `.` between two such characters or a single `,` between two digits; every other character separates words (`milk<sep>xyzzyqq` as one term matched the `milk` products when `<sep>` was `-`, `/`, `+`, `&`, `,`, or `:`, and none when it was `.` or `_`, probed 2026-10-13 and again on 2.x 2026-11-24 for `-`, `,`, and `.`; `lait 1,5%` requiring `1` and `5` matched 27 products, requiring `1,5` 324). Uppercase `AND`/`OR`/`NOT`/`TO` are operators to its parser and lowercase ones are words, and the query is lowercased and escaped before it is sent.
- **A query costs clauses per word.** 2.x matches each word against every name field of every language sent (64 fields for the 32 `langs` entries) and its other full-text fields; live 2026-11-24, 60 words still answered normally. The tool bounds `query` at 24 words, its own bound on what one query costs the backend, not the backend's. The service raises any `errors` envelope in a 2xx answer as `upstream_error` rather than reading it as zero matches.
- **A refused search is a 4xx with an `errors` list.** 2.x answers a search it refuses or fails with `{"debug": {…}, "errors": [{"title": "QueryCheckError", "description": "…"}]}`, the description naming every field the query named that the index lacks, one per line. The service puts each entry's `description`, else its `title`, in the message, and keeps up to 16 KiB of the body, where the framework's default 500 bytes cut such a body into JSON that no longer parses; the message excerpt is cut at 200 characters.
- **A POST that fails validation answers 422**, with `detail` as a list of `{type, loc, msg, input, ctx}` objects whose `input` echoes the whole request body, where a GET answers 400 with a `detail` string. An unknown `sort_by` is one such failure. The service surfaces the `msg` strings.
- **An answer flagged `timed_out: true` is not an answer.** Elasticsearch stops collecting when its own budget runs out and the backend still answers HTTP 200 with the whole success shape over a partial or empty result, so `hits`, `count`, and `is_count_exact` describe only what was collected. The service raises it as the retryable `upstream_timeout` inside the retry boundary, before the envelope check, on both `/search` and `/autocomplete`; read as an answer, an empty `options` list would cache `no_match` for a tag that exists.

### Taxonomy endpoints

`/labels.json`, `/categories.json`, `/facets/categories.json` on `world.openfoodfacts.org` return HTTP 503 for anonymous bot requests (rate-limited, requires registered session) — **not usable**. Two other surfaces are, both live-probed with this server's identifying User-Agent:

**Autocomplete (`https://search.openfoodfacts.org/autocomplete`)** — the resolver `off_browse_taxonomy` uses.

```
GET /autocomplete?q=hummus&taxonomy_names=category&size=10
{"took":1,"timed_out":false,"options":[{"id":"en:hummus","text":"Hummus","taxonomy_name":"category"}]}
```

- `taxonomy_names` accepts `category`, `label`, `allergen`, `additive`, `country`, `ingredient`, `brand`, comma-separated. There is no `nova_group` or `nutrition_grade` taxonomy; naming one answers HTTP 200 with an empty `options` list, as does an unknown name or an empty `q`.
- `size` caps the option count and the endpoint honors any value: `size=201` answers 201, and `a` on categories answers 249 at every size from 500 to 20,000, so 249 is everything that term matched. The largest answer measured is 1,313 (`c` on categories, live 2026-10-30), and a lookup asks for 2,000. `size` is the **only** paging knob — `offset`, `from`, and `page` are accepted and silently ignored, all returning the same first page — so a `size` above a term's whole answer is the only way to read all of it.
- No match total is reported. The endpoint is a suggester, not an enumerator: it cannot list a facet and cannot say how many tags matched, though an answer shorter than `size` is the term's whole answer and its length is the count.
- An answer always carries an `options` list, empty when nothing matched. A 2xx body without one is malformed and raises the retryable `upstream_error`: `off_browse_taxonomy` then takes its offline fallback, and tag canonicalization reports `lookup_failed` with cause `unavailable` and caches nothing, so the next call asks again. Read as "no suggestions", it would cache `no_match` and refuse an exclusion as unrecognized on every later call.
- Matching is against **display names**, not tag IDs, and falls back to loosely-related suggestions when nothing matches well. Ordinary words resolve cleanly (`hummus`→`en:hummus`, `tofu`→`en:tofu`, `gluten`→`en:no-gluten`), and note that category tags are frequently plural upstream: `kombucha` resolves to `en:kombuchas`, not `en:kombucha`. Ingredient tags run the other way, singular (live 2026-11-08: `inulin` → `en:inulin`, `oat` → `en:oat`, `eggs` → `en:egg`, `oats` → none). An E-number term answers the whole additive vocabulary (650 tags, live 2026-10-30), not the tag: `e314` returns all of them with `en:e314` 229th, so a request that stops short of the vocabulary misses a tag that exists, and the substring gate (see `taxonomy-service`) is what picks the match out.
- Upstream `took` is 1–3 ms; wall-clock round trip from a US client is ~0.5–0.8 s.

**Static dumps (`https://static.openfoodfacts.org/data/taxonomies/{categories,labels,allergens,additives,countries}.json`)** — HTTP 200, ~7.4 MB combined (4.6 MB / 1.2 MB / 10 KB / 906 KB / 722 KB). Not used: the payload would ship inside the npm package and the `.mcpb` bundle, needs build-time refresh tooling, and goes stale between releases. Entry counts, for scale against the in-process sample: categories 14,552 (sample 73), labels 3,037 (25), additives 683 (44), countries 268 (30), allergens 27 (14). They are still the authority on which IDs are canonical — every embedded ID is checked against them, pinned by `tests/fixtures/canonical-tag-ids.ts`. Entries carry parent/child hierarchy and per-language names but no product count, and neither does the autocomplete endpoint, so the tool reports no per-tag count.

**Brand synonym table (`src/services/taxonomy/brand-synonyms.ts`).** The static `brands.json` dump carries no synonyms, so it cannot say which names one brand entry lists. The groups ship as generated data instead: factual brand-name data copied from Product Opener's `taxonomies/brands.txt` at one openfoodfacts-server commit that the module header names, as the nutrient and unit tables are copied from `taxonomies/nutrients.txt` and `taxonomies/units.txt`. `bun run brands:sync [<40-char sha>]` regenerates it (the commit in the header when no SHA is given). At `c6a9ede` it holds 195 groups with 243 extra keys. Blocks that define one ID merge, as Product Opener merges them, and the generator writes nothing when two IDs claim one key or when an ID it computes is missing from `static.openfoodfacts.org/data/taxonomies/brands.json`. A synonym added upstream after the pinned commit matches its own key alone until the table is regenerated.

## Tools — Full Specification

### `off_get_product`

**Description:** Fetch a packaged food product by barcode (4–40 digits: EAN-13, EAN-8, UPC, and the shorter and longer codes Open Food Facts also holds) from Open Food Facts. Returns the product name and generic name, brand, quantity, ingredients (raw text and parsed list), declared allergens, trace allergens the label warns about, additives, the product-level vegan/vegetarian/palm-oil analysis, computed scores (Nutri-Score a–e and Green-Score, each with the points behind its grade, and NOVA 1–4), the low/moderate/high levels of fat, saturated fat, sugars, and salt Open Food Facts computes, nutrition per serving and per 100 g, or per 100 ml for liquids, categories, labels, packaging, origins, countries of sale, image URL, data completeness, and when the record was last modified and created. The ingredients text is in the record's main language, named by lang, and can be a contributor's translation rather than what the pack prints; ingredients_text_languages carries the text in every language entered, and image_ingredients_url and image_nutrition_url link the label photos to check it against. Open Food Facts is a crowd-sourced database — a missing field means "not yet entered by contributors," not that the attribute is absent from the actual product. Nutrition is the exception: Open Food Facts returns one preparation state per read, so a read of prepared figures (_prepared keys under nutriments) omits as-sold figures the record can still hold; when that happens, one more product read fetches the as-sold set the record stores into the as-sold fields, and nutriments.stored_as_sold says whether it was read, the record stores none, or it could not be read. Computed scores carry regional formula caveats and are indicators, not absolute rankings; Nutri-Score points rank products of one kind only. Data is under ODbL 1.0 — cite Open Food Facts in downstream use.

### `off_search_products`

**Description:** Search Open Food Facts by full-text query, structured tag filters, or both at once. Returns a summary list with barcodes, product names, brands, quantity (which tells pack sizes of one product apart), Nutri-Score, NOVA group, Green-Score, categories, data completeness, and when each record was last modified and created — enough for triage and selection, not full label data. Use off_get_product on the returned barcodes for complete details. A text query and tag filters combine: every word of the query must match the product name or generic name, and every filter provided must hold (e.g. query "dark chocolate" with labels_tag "en:organic" and countries_tag "en:france" returns organic chocolate sold in France). The query searches names only, so express a category, label, or brand as categories_tag, labels_tag, or brands_tag rather than as query words. Numeric nutrient_filters express thresholds per 100 g, or per 100 ml for liquids, such as sugars below 8 g, each compared as given, and combine the same way; they reach only products whose text-index entry carries the constrained nutrient, and each row then carries the indexed values the thresholds were compared against. ingredients_tag takes canonical ingredient IDs (e.g. "en:inulin") that must all appear among the ingredients Open Food Facts parsed from the label, and combines the same way. nutrition_grade, nova_group, and ecoscore_grade (Green-Score) each take one grade or an array matching any of them. Tag filter values are canonical tag IDs (e.g. "en:organic", "en:no-gluten") — use off_browse_taxonomy to resolve human terms to tag IDs. A case variant, synonym, or singular of a tag is resolved to its canonical ID where Open Food Facts recognizes it; anything else is matched exactly. exclude_allergens and exclude_traces drop products that declare an allergen or a "may contain" trace, but a product with no allergen or trace data entered passes them, so confirm a candidate with off_get_product before relying on it. At least one search parameter is required. The two paths read different indexes: a search carrying query, nutrient_filters, or ingredients_tag is answered by the text index, a snapshot that lags the live database and whose newest record text_index_as_of dates, while a tag-only search reads the live database and is current, or, where this server keeps a local copy of the Open Food Facts export, can be served from that copy, which source and mirror_as_of then report and whose default order and popularity_key or unique_scans_n sort follow the values stored with each record, so they can differ from a live search, which ranks by its current scan counts — so a recently contributed product can be missing from a text search and present in the same search without query. Data is crowd-sourced; result count reflects contributed products, not all products in the market. Data under ODbL 1.0 — cite Open Food Facts in downstream use.

**Input schema:**

The `page_out_of_range` check runs in the handler before the service is called, mirroring the `no_filters` pre-check. It keys on which backend will answer, not on `query` alone, so a nutrient-filtered or ingredient-filtered search with no free text is subject to the text path's bound. `page_out_of_range` applies each backend's own bound: past page 10 on the live tag path, whatever the `page_size`, and `page * page_size` beyond 10000 on the text path and on the mirror; its recovery hint names the deepest page that can be requested. A tag-only search the mirror can serve is held to the mirror's window, not page 10: the handler asks the service whether the mirror is ready (`mirrorReady`) before the page check, and, for a search carrying `ecoscore_grade`, whether its last completed full load indexed Green-Score (`mirrorIndexesGreenScore`), counting the mirror as not ready until one has, and, for a search carrying `brands_tag`, whether it keyed every brand (`mirrorIndexesBrandKeys`), counted the same way. It refuses a page past 10 only when no mirror is ready, when canonicalization shows a value the mirror cannot match (a brand it cannot match, because none of its keys is held or no full load has keyed every brand yet, is settled by one live count instead: a page the live matches end before is answered empty with that total, and a total that reaches into the page is refused naming `data.brand` and `data.live_total`), or when the service answers `page_out_of_range` with `bound: 'live_max_page'` because the mirror could not serve the search after all; all of them throw `page_out_of_range`, and a ready mirror that has not indexed Green-Score does so with a message naming `ecoscore_grade` and the reload that lifts the bound. Once every value is confirmed, a page past the mirror's window is refused before the service is called, in the text-window refusal's shape (`max_page` at the served `page_size`, `result_window`, and a hint to narrow the filters or change `sort_by`), and the service answers `bound: 'mirror_window'` for one that reaches it. Every page computation uses the `page_size` served — `min(page_size, 100)` — so `{query: "chocolate", page: 101, page_size: 200}` is refused with `max_page: 100` and a hint at `page_size` 100, while page 100 is sent at 100; the served size is echoed as `page_size` and, when it differs from the one requested, disclosed in the `page_size_capped` enrichment with the next page to request when one holds matches and can be requested. `query_too_long` runs there too, counting runs of letters and digits in `query`.

A page whose every row left, for an unservable code, reads "lists no products", never "No products found" or "past the end of this result set", because the search is matching rows. One function, `emptyPageNextStep`, writes its ending for the notice and for `format()`: a next page exists, so request it; otherwise no further page of matches can be requested. An unservable code is no reason to change the search, so nothing there suggests narrowing it.
On the text path the handler then runs every string tag filter value (`categories_tag`, each `labels_tag` and `ingredients_tag` value, `allergens_tag`, `traces_tag`, `countries_tag`) and the `additives_tag` through the taxonomy service's `canonicalizeTag` before the service quotes it (see "Text search" and the taxonomy service); `traces_tag` resolves against the allergen vocabulary, since trace tags are allergen tags, `ingredients_tag` against the ingredients vocabulary, and `additives_tag` against the additives vocabulary. A brand has no vocabulary and is never looked up: `brandKeys` computes its keys, and each backend receives them in its own form (see the brand decision). A response carrying an exclusion gets the `exclusion_coverage` enrichment on both surfaces: products with no allergen or trace data entered pass an exclusion, so check a candidate with `off_get_product`. The tag path sends an allergen or trace inclusion and its exclusions as one parameter (`allergens_tags=en:nuts,-en:milk`) and several labels as one comma-joined `labels_tags`; the text path sends one clause per value, exclusions as `-field:"value"` after the inclusions. A text-path search that matches nothing gets a notice naming the causes that apply to it: a query word no product carries (when `query` was sent), the field name of a `field:value`-shaped word, which had to match as a word too (`brands: nutella` → 0, live 2026-09-23), exact tag matching with each value no vocabulary confirmed and what was sent for it (when tag filters were sent; a brand's stated reason is how a brand is matched: as given, under its slug, and under every other name of its Open Food Facts brand entry, any of which matches, never as part of a name), and index lag. `off_browse_taxonomy` holds no brands, so the pointer to it covers only the other tag filters and a brand alone gets none, and a tag-only zero tells the caller to check the brand's spelling and states how a brand is matched. ### `off_compare_products`

**Description:** Side-by-side nutrition and scoring comparison for 2–10 products per call by barcode; a repeated barcode is compared once, so two identical barcodes yield one row, and barcodes past the 10th distinct one are listed in unprocessed rather than fetched. Returns a normalized table of energy (kcal), fat, saturated fat, carbohydrates, total carbohydrates including fiber, sugars, salt, protein, and fiber per 100 g, or per 100 ml for liquids, plus Nutri-Score and Green-Score, each with the points behind its grade, and NOVA group. Open Food Facts returns one preparation state per read, so figures for the prepared product arrive in a prepared object on the row, with the same columns and basis, and never fill an as-sold field; a row whose read returned only prepared figures gets one more product read, of the as-sold set its record stores, once the read of every barcode has settled, with stored_as_sold saying how it went. Designed for "which of these cereals is healthiest?" or "compare these pasta brands" workflows. Missing nutrition data for any product is preserved as absent — comparisons are not imputed. A batch is not all-or-nothing: barcodes that resolve are returned even when others fail, with confirmed-missing barcodes listed in not_found and failed fetches listed separately in failed. Scores carry regional formula caveats; Nutri-Score points break a grade tie only between products of one kind. Data under ODbL 1.0 — cite Open Food Facts in downstream use.

No DataCanvas spill: a batch caps at 10 products, which is too small to warrant a canvas/SQL layer.

**Over-cap batches are served, not refused.** A batch of 11–100 barcodes has one obvious reading, so it compares the first 10 distinct barcodes and lists the rest in `unprocessed` (and a `format()` line, "Not compared (over the 10-barcode cap)") instead of failing with `invalid_arguments`; 100 stays the hard ceiling. **Errors:** Declares `upstream_error`, `upstream_timeout`, `upstream_rejected`, and `rate_limited` — the same four reasons the service raises, with recovery text scoped to a batch ("retry the barcodes listed in failed"). None of them aborts the call: a batch is not all-or-nothing, so each is surfaced per barcode in `failed[]` while the rows that resolved are kept. Confirmed-missing barcodes stay in `not_found`, which claims the opposite of a failed fetch.

### `off_browse_taxonomy`

**Description:** Resolve a human term to the canonical Open Food Facts tag ID that off_search_products filters on. Covers categories, labels/certifications, allergens, additives, countries, ingredients, NOVA groups, and Nutri-Score grades. Pass a search term to resolve against the Open Food Facts vocabulary, which holds tens of thousands of tags; omitting it returns only a small reference list for each facet except NOVA groups and Nutri-Score grades, which are complete, and ingredients, which has no reference list and returns nothing. Most tag IDs use the "en:" prefix (e.g. "en:organic", "en:no-gluten", "en:crustaceans"); NOVA groups return bare digits "1"-"4" and Nutri-Score grades bare letters "a"-"e". Pass the id through to off_search_products exactly as returned. Category tags are frequently plural ("kombucha" resolves to "en:kombuchas") and ingredient tags singular ("oat" resolves to "en:oat", "oats" to nothing), so use the returned id rather than constructing one.

### `openfoodfacts-service`

- **Base URL:** `https://world.openfoodfacts.org`
- **User-Agent:** `openfoodfacts-mcp-server/<version> (casey@caseyjhand.com)` — sent on every request. Required by OFF terms.
- **Field selection:** every call includes `fields=` to scope the product object.
- **Methods:**
  - `getProduct(barcode, ctx)` and `getProductFields(barcode, fields, ctx, predated?)` → a `ProductRead` (`{ source: 'off_api', product }`, or `{ source: 'off_mirror', mirrorAsOf, product, storedSets, unread? }`) or `null` (status:0). The mirror is read first by barcode, normalized as Product Opener normalizes it, and a miss falls through to the live read. `getProduct` serves every field the product tool requests; `getProductFields` reads the mirror only when each requested field is one the mirror holds. A mirror read's `product` takes the doc's fields plus `created_t` and `last_modified_t` from the row's columns. Either reads live first for a row whose record version predates a requested field (`generic_name` and `nutrient_levels` arrived in version 2; `lang`, `ingredients_text_languages`, `nutriscore_score`, `ecoscore_score`, `image_ingredients_url`, and `image_nutrition_url` in version 3; the dates are columns, so no record version predates them), and serves the row when that read raises a declared failure or finds no product, `unread` naming the fields it lacks and how the live read ended (`{ outcome: 'failed', error }` or `{ outcome: 'not_found' }`). `predated` is `read_live` (that behavior, the default) or `serve_row`, which serves the row at once with `unread` naming the fields `{ outcome: 'skipped' }` and sends nothing; `off_compare_products` passes `serve_row`. The caller's cancellation, and anything that is not a declared failure, is rethrown.
  - `mirrorHeldBrand(keys, ctx)` → the ones of a brand's keys (`brandKeys`, in order) that a product the ready mirror holds carries, which the mirror search then takes as one any-of filter, or `undefined` with no ready mirror, none held, or a store error (logged), so the search reads live. A brand is held when any of its keys is. Ask only once `mirrorIndexesBrandKeys` holds. The caller's cancellation is rethrown.
  - `mirrorIndexesBrandKeys(ctx)` → whether the mirror is ready and its last completed full load was built at `BRAND_KEY_RECORD_VERSION` (4) or later, so every row holds a brand under its key; false with no mirror, a store not ready, or a store error (logged). Beside `mirrorIndexesGreenScore`, it keeps a tag-only search carrying `brands_tag` live until such a load completes.
  - `readStoredAsSold(barcode, ctx, read)` → `{ status: 'read', nutriments }`, `{ status: 'none' }`, or `{ status: 'unread', error }`, taken from the same source as `read`. A mirror read selects from its `storedSets` with no request and no budget slot. A live read calls `GET /api/v3.5/product/{barcode}?fields=nutrition.input_sets`, then `selectAsSoldSet` over the sets, never the mirror, whose record can be a different revision. Each live attempt spends a product-budget slot. A 404 after the product read found the barcode means the route, not the record, is missing, so it is `unread` (`upstream_error`) at once, never `none`. Every other declared failure is `unread` with its reason; the caller's cancellation, and anything that is not a declared failure, is rethrown.
  - `mirrorReady(ctx)` → whether the mirror is configured and ready (a sync has completed and the store holds products); false without building a store when `OFF_MIRROR_PATH` is unset or names no file, and false on a store error, which is logged.
  - `searchProducts(params, ctx)` → `{ status: 'served', source, mirrorAsOf?, textIndexAsOf?, count, count_is_exact, page, page_count, page_size, products[], dropped }` (the `SearchResult` type plus the `source` — one shape from every backend; `textIndexAsOf`, the text index's newest `last_modified_t` as an ISO 8601 time when the service holds it, exists only on the text path), or `{ status: 'page_out_of_range', bound }`, with nothing sent and no search run: `live_max_page` for a `tags_confirmed` search the mirror could not serve at a page past 10, `mirror_window` for one the ready mirror would serve at a `page * page_size` past `MIRROR_SEARCH_RESULT_WINDOW` (10,000). Routing: `query`, `nutrient_filters`, or `ingredients_tag` → text index (an ingredient filter whatever `tags_confirmed` says, since the mirror indexes no ingredients and `/api/v2/search` stops at page 10); tag filters alone with every value confirmed (`tags_confirmed`: taxonomy values by vocabulary, a brand by the keys the mirror holds products under) → mirror when ready (for `ecoscore_grade`, when its last full load indexed Green-Score; for `brands_tag`, when it keyed every brand), an exact `count` on every page; otherwise `/api/v2/search`. A grade input moves no search between backends, and each backend takes several grades its own way: an any-of group on the mirror, a `|` list on `/api/v2/search`, an `(a OR b)` group on the text index. Every row carries a `code` matching `BARCODE_PATTERN`, the rule the product tools enforce: a row without one is dropped on either path before `page_count` is set, so `page_count` always equals the rows returned and every `barcode` passes `off_get_product`'s schema. No row without any `code` has been observed, but the text index holds 664 codes Product Opener refuses (`00000###`, `0000000000###`); the drop is logged with the codes.
  - The text path (`buildTextSearchQuery`) builds its Lucene `q` as tag clauses (one per value, under the 2.x field names `categories`, `brands`, `labels`, `allergens`, `traces`, `additives`, `countries`, plus `ingredients_tags` and `ingredients_analysis_tags`), grade clauses (`nutriscore_grade`, `nova_group`, `environmental_score_grade`; an `(a OR b)` group for several grades of one input), exclusion clauses (`-allergens:"value"`, `-traces:"value"`), nutrient range clauses with each bound as given, then the query's words, lowercased, space-separated, and escaped (`textQueryTerms`, which extracts them with `ANALYZER_WORD`: runs of letters, marks, digits, and `_`, joined across a single `'`, `’`, or `.`, or a `,` between two digits; every other character separates, so `milk-chocolate` is two words). It sends `q` with `langs` set to `TEXT_SEARCH_LANGS` (31 codes and `main`) and `fields` set to `TEXT_SEARCH_RESULT_FIELDS`, the summary fields under the index's names: `categories` and `environmental_score_grade` for the rows' `categories_tags` and `ecoscore_grade`, which `searchProductsByText` maps back, and `brands` tag IDs, which each row shows with the leading `xx:` dropped and comma-joined (`["xx:heinz", "xx:Member's Mark"]` → `heinz, Member's Mark`). A value sent under several IDs, a brand's or a taxonomy value's, forms one quoted any-of group.
- **Rate limiting:** token bucket per endpoint class — product reads (15/min), search (10/min), taxonomy resolution (10/min). A refusal is local, so it raises `rate_limited` (`RateLimited`) naming this server, not Open Food Facts, and carries the seconds until a slot frees. A best-effort request, the text index date probe, takes a slot with `tryAcquireSpare` only while two or more are free and is otherwise not sent, so it never takes the last slot and never throws; the slot it takes counts against the search budget like any other.
- **Transport:** `fetchWithTimeout` at every call site, so HTTP status → error code, canonical `status`/`body` on the framework's fetch error (the public contract republishes a selected subset of it — see the error-contract allowlist below), `Retry-After` honoring, and distinct `Timeout` classification all come from the framework rather than a hand-rolled status ladder.
- **Retry:** `withRetry` on the full fetch+parse pipeline. Up to 4 attempts, 500ms base delay on product and autocomplete reads and 1s on searches (upstream is stateless; 5xx is transient). Classification runs *inside* the retry boundary so the mapped reason decides: a 5xx other than 501, timeouts, and 429 retry; a 4xx or a 501 fails immediately.
- **Deadline:** every read passes `deadlineMs` to `withRetry` through one wrapper, `retryRead`, and threads the attempt's `signal` into its request, so an expiry cuts off the request in flight. A product or search read has 35 s across all attempts and backoffs (`READ_RETRY_DEADLINE_MS`) and an autocomplete lookup 20 s (`TAXONOMY_RETRY_DEADLINE_MS`). A search runs its tag lookups in parallel and then one search read, so one caller's longest chain is 20 s + 35 s = 55 s, and a batch comparison is one 35 s ladder wide, not N long. The stored as-sold read (`readStoredAsSold`) has its own 20 s (`AS_SOLD_RETRY_DEADLINE_MS`), counted from when the product read it follows has settled, so a call settles within 35 s + 20 s = 55 s; a comparison starts these reads only after every product read has settled, so its chain stays 55 s too. Expiry there ends as `{ status: "unread", reason: "upstream_timeout" }`, never a thrown error. A lookup's 20 s run from its caller's call to `canonicalizeTag`: a caller restarting a shared lookup its starter cancelled passes `suggestTaxonomy` only what is left, so the restart stays inside the same 55 s. Against an upstream that never answers, a product or search read makes 3 attempts and a lookup 2 (15 s per attempt plus backoff), so "up to 4 attempts" is a ceiling the deadline usually cuts short. Expiry leaves the service as `upstream_timeout`, carrying the call's own fields (`barcode`, or `page`/`page_size`, or `taxonomy_name`/`term`) and `operation`; the framework's `retry_deadline_exceeded` is declared by no tool and never reaches a caller. A read whose last finished attempt answered 429 reports that 429 as `rate_limited` with its `retryAfter` instead, because it is a limit to wait out, not an outage; an attempt the expiry cut off finished nothing and leaves the 429 standing, and any attempt that did finish replaces it, a 15 s timeout included. A caller abort is ranked above the deadline and ends as cancelled.
- **Parse failure:** HTML error pages (503 during high load) detected by content-type check, and any 2xx body that does not parse as JSON, → `upstream_error` (`ServiceUnavailable`, not `SerializationError` or a reason-less `ValidationError`).
- **Malformed envelope:** a 2xx JSON body that fails its read's rule — product: `status: 0`, or `status: 1` with a `product` object; stored sets (v3.5): `status` `success` or `success_with_warnings`, `result.id` `product_found`, and a `product` object whose `nutrition`, when present, is an object with `input_sets` a list; tag search: a `products` list and a numeric `count`; text search: `hits`, a numeric `count`, and a boolean `is_count_exact`; autocomplete: an `options` list — raises `upstream_error` inside the retry boundary, like an HTML page served with a 200. No `?? 0` / `?? []` default turns it into an answer. A text search or autocomplete body flagged `timed_out: true` raises `upstream_timeout` first, however complete its shape.
- **Stalled body:** `fetchWithTimeout` returns at the response headers and hands its deadline to the body, so a body that stalls fails inside `parseJsonBody`, outside the contract mapping around the fetch. `parseJsonBody` maps it there, so it leaves as the same typed failure rather than a raw framework timeout.
- **Refused text search:** a 4xx whose body is a 2.x `errors` list is `upstream_rejected`, and its message carries each entry's `description`, else its `title` (`upstreamDetail`). The text POST keeps up to 16 KiB of an error body (`TEXT_SEARCH_ERROR_BODY_LIMIT`), since a `QueryCheckError` names every rejected field on a line of its own and the framework's 500-byte default cuts such a body into JSON that no longer parses; the message excerpt is cut at 200 characters.
- **Missing barcode:** `status:0` in a 200 response, or an HTTP 404, → `null` from the service; the handler calls `ctx.fail('not_found', ...)`. `null` is reserved for this case alone.

### `taxonomy-service`

Owns resolution policy for `off_browse_taxonomy`; transport lives in `openfoodfacts-service.suggestTaxonomy()`, which carries the same `fetchWithTimeout` / `withRetry` / contract-error plumbing as the product and search paths plus its own rate-limit tier.

- **Facet routing.** `categories`, `labels`, `allergens`, `additives`, `countries`, `ingredients` map to the upstream `category`/`label`/`allergen`/`additive`/`country`/`ingredient` taxonomies. `nova_groups` and `nutrition_grades` have no upstream counterpart and are closed vocabularies, so they are answered entirely from the embedded map and are the only facets that report `total_in_facet`.
- **Embedded sample.** A static `facet → [{id, name, aliases?}]` map: 73 categories, 25 labels, 14 allergens, 44 additives, 30 countries, 4 NOVA groups, 5 Nutri-Score grades. For the five live facets that have one this is a small slice (categories is 73 against 14,552 upstream), used for unfiltered listing, offline fallback, and as the leading half of a merge. `ingredients` has no sample (see "Ingredients has no offline sample"). Every ID is a canonical key in the static dumps, because a synonym or singular form is not rejected anywhere downstream — it filters nothing and reports the zero as exact. A human term with no canonical key of its own (shellfish, cookies, gluten free) rides on `aliases`, which widen what a search resolves and never reach the caller; a term with no canonical key at all (mixed salads, chocolate bars, the per-nut allergens) is left out rather than approximated, and the live merge still resolves it.
- **With a search term.** The embedded matches and the live suggestions are merged, embedded first, deduplicated by tag ID, the tag the term names moved to the front (next bullet), then capped at `limit`, which the tool holds to 200 and which has no input maximum: a larger `limit` returns the first 200. Whenever the limit cuts matches, the truncation guidance names the match count and a call that can bring more forward: a larger `limit` below the cap (or a narrower term), and at the cap — a `limit` of 200 included — only a narrower term, plus the limit asked for when it was above 200. Upstream is asked for 2,000 suggestions, not `limit + 1`, so the lookup reads the term's whole answer and the match count is exact below that size (see "The live suggestion pool is requested in full").
- **The exact-term tag ranks first among the live suggestions.** After the substring gate, live entries whose ID is `en:<slug>`, `en:<slug>s`, or `en:<slug>es` (`<slug>` = the lowercased term, whitespace runs hyphenated) are stable-sorted ahead of the rest, which keep upstream order. Only an equal ID moves, so `en:red-lentils` is never promoted for "lentil"; the embedded block keeps its own order ahead of the live portion, behind the tag below.
- **The tag the term names leads the merged list.** One accept rule, `confirmedTag`, serves `canonicalizeTag`, `resolveLive`, and `search()`, so the first row browsing lists is the tag a filter on the same term resolves to. It confirms at most one entry: from the sample, one whose ID equals the normalized term or whose name equals it; else, from the whole live answer, one whose ID equals it, one whose name equals it (the autocomplete's `text`, the synonym the term matched, which the merge replaces with the sample's display name when both hold the tag), or one whose ID is its plural. That entry moves to the front from either source. When the substring gate dropped it because the term spells with spaces what the tag spells with hyphens (`plant based milk alternatives`), it is added at the front, as the sample lists it or else as the live answer did, and counted in `matched_in_facet`. Nothing else moves, and a term nothing confirms (`cereal`, `tomato`, a truncated `chees`) keeps the order above.
- **Live suggestions are held to the facet's documented substring rule.** Upstream matches display names and degrades to loosely-related suggestions rather than returning nothing, so unfiltered pass-through would answer `e330` with E-numbers that do not contain it. Applying the same `id`/`name` substring predicate used for the embedded half drops that noise; measured across ordinary terms (cheese, kombucha, olive oil, organic, tofu, yoghurt, …) it drops nothing else. The tag the accept rule confirms is exempt: it reads hyphens as spaces where the gate does not, so a term spelled with spaces can miss the gate and still name the tag.
- **Without a search term.** The embedded sample only, plus a `notice` saying so; `ingredients`, which has no sample, lists no tags and the `notice` asks for a term. The upstream endpoint suggests against a term and answers an empty list for an empty query — it cannot enumerate a facet.
- **On failure.** The throw is absorbed and the offline matches returned, the tag the sample confirms for the term leading them (added, and counted, when the gate missed it), with a `notice` naming the cause; `ingredients` returns no tags, and its `notice` says the empty list does not mean the term has no tag. A caller cancellation is not absorbed: with `ctx.signal` aborted the error is rethrown and the call ends as cancelled (`RequestCancelled`), never as the offline fallback. `openWorldHint: true`.
- **Tag-value canonicalization (`canonicalizeTag(facet, value, ctx)`).** Used by `off_search_products` for every taxonomy tag value on the text path, where tag fields match exactly, and for every exclusion value on both paths. `facet` is a `LiveFacet`, a facet the live autocomplete serves: a brand has no vocabulary and never comes here. Returns `{value, resolution: 'vocabulary'}` when a tag with that ID is confirmed, or `{value, resolution: 'normalized', reason}` otherwise, with `reason` `no_match` or `lookup_failed`. A `lookup_failed` carries `cause`: `budget_spent` when this server's taxonomy budget refused the lookup and nothing was sent (with `retryAfter`, the seconds until a slot frees), `rate_limited` when Open Food Facts answered 429 (with `retryAfter` when it sent a readable `Retry-After`), or `unavailable` for everything else — unreachable, a 5xx, a timeout, a malformed or timed-out answer, a refusal, an expired lookup deadline. Only the budget refusal's type (`BudgetExhaustedError`) tells the first two apart, since both arrive as the declared `rate_limited` failure; every surface that reports an unchecked value words it by cause and names the wait, and only `unavailable` says the vocabulary could not be reached. A taxonomy value is checked against the offline sample, then the live autocomplete (taxonomy budget, the term's whole answer), accepting only an entry whose ID equals one of the value's `taxonomyTextIds` (the normalized value, then, for a value ending in a capital sigma, the ID of its whole-string lowercase, whose word-final `ς` an entry built from a name written in lowercase carries: `EL:ΣΑΛΑΤΕΣ` confirms `el:σαλατες`) or whose name equals the value with its `xx:` prefix stripped, compared case-insensitively with hyphens read as spaces — the embedded `aliases` are not used, since they are wider than upstream synonyms — or, from the live pool only, an entry whose ID is the value's plural: the value plus `s`, or plus `es` after `ss`, `x`, `z`, `ch`, `sh`, or `o`. That is `confirmedTag`, which settles on the first match in the order sample, live ID, live name, live plural, and which browsing uses to lead with the tag a filter on the same term resolves to. An `ingredients` value has no sample, so it always takes the lookup (`eggs` → `en:egg` by name; `oats` confirms nothing). The autocomplete answers `nut` with `{id: en:nuts, text: Nuts}`, so the name rule alone cannot confirm `en:nut`, which Product Opener canonicalizes to `en:nuts` (and it counts `en:chocolate` exactly as `en:chocolates`, 32,689, live 2026-09-23). `es` is narrower than `rankExactTagFirst`'s ranking rule because after any other stem it resolves a truncated word: `ric` would become `en:rices` and `chees` `en:cheeses`, while Product Opener counts `en:ric` as 0. Unmatched values are normalized the way Product Opener stores an unknown tag: the language prefix (English when absent) plus the slug of the rest (`US` → `en:us`). It throws only on a caller cancellation, which ends the call rather than returning `lookup_failed`; settled answers are cached in process per facet and the value's `taxonomyTextIds`, up to 500 entries, oldest evicted first, and a failed or cancelled lookup is not cached. The key is every ID, not the normalized one alone: `EL:ΣΑΛΑΤΕΣ` and a typed `el:σαλατεσ` normalize alike, but only the first can be confirmed by `el:σαλατες`, so under one key whichever was looked up first would decide the other's answer. Concurrent calls for the same facet and IDs share the lookup in flight, which leaves the map once it settles, so a failure is still retried by the next call. A shared lookup rejects only when the caller that started it was cancelled, so a joined caller whose own signal is live starts over instead of inheriting that cancellation: the first one back starts the replacement lookup within what is left of its own 20 s, counted from its call, and the others join it. A caller left nothing reads `lookup_failed` with cause `unavailable` and sends no request. A caller that must never send an unconfirmed value, such as an exclusion (which a wrong value turns into a silent no-op), refuses anything but `vocabulary`.
- **Brand keys (`brand-keys.ts`, `tag-id.ts`, `brand-synonyms.ts`).** A brand has no vocabulary to confirm it, so one function, `brandKeys(given)`, computes every key it can be stored under, and the record builder, the mirror query, the live tag path, and the text path all call it. `brandSlug` is the slug of the brand name under the `xx` normalization Product Opener's `get_string_id_for_lang` gives a brand (NFC, lowercase one character at a time as Perl's `lc` does, `.` and punctuation/whitespace to `-`, dash runs collapsed and trimmed, and a fixed set of accented Latin letters folded: `Nestlé` → `nestle`, `Meßmer` → `messmer`; every other letter, `ø` and `ł` included, kept, so `Løgismose` → `løgismose` and `ブルボン` is unchanged), after any two-letter language prefix is dropped: Product Opener answers `brands_tags=xx:nutella` and `=en:nutella` with the 488 products `=nutella` matches (live 2026-11-01), while slugging the prefix would send `xx-nutella`, which no brand carries. `brandKey` is that slug with sigma case-folded (`ς` → `σ`), because the per-character lowercase turns an all-caps `ΌΛΥΜΠΟΣ` into `όλυμποσ` while `όλυμπος` typed in lowercase keeps its final `ς`, and both must key alike; `xx:Красный Октябрь`, `xx:красный-октябрь`, and `красный-октябрь` all key as `красный-октябрь`. `brandKeys` is the key first, then, when the key is a name of a `taxonomies/brands.txt` entry (`BRAND_SYNONYM_GROUPS`), the key of each of the entry's names, its canonical ID's first (`7-Up` → `7-up`, `7up`, `seven-up`; `Andechser` → `andechser`, `andechser-natur`). A brand in no entry has its own key alone (`nutell` → `nutell`, which matches nothing): an entry matches a whole key, never a substring. Each backend gets the keys in its own form. The mirror holds each brand as a `brands:xx:<key>` posting and searches the keys it holds as one any-of filter. `brandLiveIds` sends `/api/v2/search` the brand as given, then `xx:<key>!` for each key that differs from it, which Product Opener matches as that exact stored tag; a brand that keys to itself goes as given alone (`Красный Октябрь|xx:красный-октябрь!` matches 23 products live 2026-11-24, 16 for the given value alone). `brandTextIds` builds the text index's any-of group (see "Text search").

### Local export mirror (`src/services/mirror/`)

An optional SQLite copy of the Open Food Facts export, enabled only when `OFF_MIRROR_PATH` is set. With it unset no store opens and no refresh is scheduled.

- **Store.** One file at `OFF_MIRROR_PATH` (WAL beside it), built on the framework's `@cyanheads/mcp-ts-core/mirror`. `products` holds one row per normalized barcode: the four `sort_by` keys, the sorted tag ids, and `doc`, the record builder's projection of what `GET /api/v2/product/{code}?fields=…` returns for the fields this server requests, so a mirror read hands the tools the same shape a live read does. `tags` and `product_tags` hold one posting per product per tag, kept in step by triggers. Each row records the `MIRROR_RECORD_VERSION` that built it; version 2 added `generic_name`, `nutrient_levels`, and the Green-Score facet (`environmental_score_tags`), version 3 added `lang`, `ingredients_text_languages`, `nutriscore_score`, `ecoscore_score`, `image_ingredients_url`, and `image_nutrition_url` (`FIELD_SINCE`), and version 4 keys each brand by its `brandKey` rather than its stored spelling (`BRAND_KEY_RECORD_VERSION`), so a build at a version above the last full load's starts a full reload. A brand is indexed as `brands:xx:<brandKey>`, whatever form the record stores it in (`xx:Красный Октябрь`, `xx:красный-октябрь`, or bare `красный-октябрь`), and no raw typed key is written. `mirror_load.record_version` is the lowest `MIRROR_RECORD_VERSION` that built any row of the load, so a load resumed under a newer builder records the older one and the next refresh reloads it. The row's `created_t` and `last_modified_t` columns are the only place a read takes a record's dates from, since `doc` never stores them, so a row of any record version is dated alike. The header of `mirror-store.ts` is the schema and index reference.
- **Lifecycle.** `mirror:init` downloads the export (`openfoodfacts-products.jsonl.gz`, resumable with `Range` and `If-Range`, restarting from byte 0 when the ETag changes), ingests it in 2,000-record pages, sweeps the rows the load did not stamp, builds the sort indexes, and then applies the deltas published since. An interrupted run resumes where it stopped. A load that stamped no product, across every run it took, stops before its sweep (`export_no_products`), leaving the store, its last full load, and its checkpoint as they were and deleting the download, which the next run fetches again. A full init of the 2026-11-01 export (4,887,190 products) took 1 h 48 min (an 8.5 min download, 93.5 min of ingest, then 4 min to build the sort indexes), peaked at about 27 GB on disk while the 13.4 GB download sat beside the store (it is deleted once ingested, before the sweep), left a 14.3 GB store, and peaked at 349 MB of resident memory. `mirror:refresh` applies each delta ending past the checkpoint, oldest first, and stops on any non-2xx with the checkpoint unchanged; at a path naming no file it is refused (`mirror_not_initialized`) before it opens anything. A line of the export or a delta that is not valid JSON or runs past 16 MiB is skipped, counted, and logged by line number. `mirror:status` prints health, including the lines the last full load skipped, and exits non-zero unless a sync has completed and the store holds products; `mirror:verify` (`mirror:status --verify`) adds SQLite's integrity check. Any of the four that meets a sync's write lock for longer than its open waits exits non-zero naming the sync that holds it. All four need a checkout or the Docker image, since the scripts resolve `@/` aliases.
- **Refresh.** The serving process schedules `MIRROR_REFRESH_SCHEDULE` (`30 */3 * * *`: every three hours at minute 30, read in the server's local time) and runs each pass as a child process, because a sync's write transactions block the event loop they run on. A cross-process lease row in the store keeps `mirror:init`, `mirror:refresh`, and the scheduled job from overlapping. A run checks the row before each page and sync-state write, so one whose lease was reclaimed (a heartbeat 5 minutes stale) writes nothing more, its failure included.
- **Serving.** `off_get_product` and `off_compare_products` read the mirror first by barcode and read live on a miss. A tag-only `off_search_products` is served when every value is confirmed (a brand when the mirror holds products under any of its keys), with an exact total, through its first 10,000 results; one carrying `ecoscore_grade` only once the last completed full load was built at version 2 or later, and one carrying `brands_tag` only once it was built at version 4 or later, so until a version-4 full load completes a brand search reads live. Every other search is live. Reads are gated per field on the row's record version: an `off_get_product` read asking for a field a row's version predates is live too, and falls back to the row without those fields when the live read fails or finds nothing, while one asking for none of them stays on the mirror. `off_compare_products` stays on the mirror through a reload: it serves a predating row as stored, with no live read, and the row names the fields it lacks in `mirror_fields_unread`. A search row's and a product's `last_modified` and `created` come from the row's columns at any record version. A store error is logged and the call is read live. The serving process checks on every call that the store's file exists, never creating one, and its open waits at most 250 ms (`SERVING_BUSY_TIMEOUT_MS`) on a sync's write lock before the call reads live; the next call checks the file and opens again.
- **Disclosure.** Each result carries `source` (`off_api` or `off_mirror`; per row on compare), `mirror_as_of` (a time up to which the copy reflects every product contributed or edited: the end of the last applied delta, or the newest change in the export a full load read; while a full load runs over a loaded store, the older of the as-of it began with and the newest change among the rows it has written), and, from the mirror, a `mirror_snapshot` note: edits reflected through `mirror_as_of`, computed values only as of the record's last edit or the last full reload (about every 30 days), whichever is later, a product removed since that reload still shown, and on a search, filters matched against the stored values, computed ones included. An `off_get_product` answer from a row that predates requested fields its live read could not supply also carries `mirror_fields_unread`, naming those fields and the live read's failure or not-found; an `off_compare_products` row from such a row carries it too, naming the fields and saying that no live read was sent for them.

## Design Decisions

**No resources.** Product data is mutable (crowd-sourced) and not suitable for stable URI caching. Tool-only clients are the primary target.

**No prompts.** The domain is data retrieval; no recurring analysis frameworks benefit from a prompt template.

**Taxonomy resolution is live, with the embedded sample kept as a merge partner rather than replaced.** The `world.openfoodfacts.org` taxonomy endpoints do return 503 to anonymous bots, but `search.openfoodfacts.org/autocomplete` does not, and the embedded-only design it justified had made the tool's advertised purpose unreachable: the sample holds 73 categories against 14,552 upstream, so ordinary foods (hummus, tofu, kombucha, pizzas) answered "no matching tags" for tags that filter thousands of products. Live resolution over a static mirror because a mirror puts ~7.4 MB into the npm package and `.mcpb` bundle, needs build-time refresh tooling, and goes stale between releases, while a suggestion costs about a kilobyte and always reflects the current vocabulary.

The sample stays because live-only would regress two cases it answers correctly. The upstream suggester matches display names and returns loosely-related suggestions instead of nothing, so an E-number term comes back as the whole additive vocabulary while the sample resolves the E-numbers it holds exactly; and an Open Food Facts outage would turn a working `en:organic` lookup into a failure. Merging embedded-first, deduplicated, with the tag the term names leading, keeps both, and holding live suggestions to the same substring rule the facet documents drops the suggester's noise without dropping real matches.

**A failed live lookup degrades with a notice instead of raising a declared failure.** No `errors[]` contract is declared for this tool, because none of its reasons could fire: the throw from `suggestTaxonomy()` is absorbed in the taxonomy service and reported through `enrichment.notice` (for `ingredients`, which has no sample, with an empty list). Declaring a reason the handler cannot return advertises a state callers would branch on and never reach — the same argument that removed the `found` flag from `off_get_product`. The degradation is not silent: the notice reaches `structuredContent` and `content[]` alike, names the cause, and says the offline sample may not cover a tag that exists upstream, so an empty result is never read as an authoritative "no such tag". This is the specific failure the tool had, and returning nothing with a raised error would reintroduce it for the callers the sample can still serve.

**`total_in_facet` is reported only for the closed vocabularies.** The autocomplete endpoint reports no match total and cannot be enumerated, so the live facets have no knowable total; the field is omitted rather than filled with the sample size. Returning `79` for categories is what presented a local sample as the size of the Open Food Facts category vocabulary.

**No offset or page input.** The endpoint's `size` caps the option count and is its only paging knob — `offset`, `from`, and `page` are accepted and silently ignored, all returning the same first page. An offset input would therefore have to be a lie or a client-side slice of one fetch; a cursor over one lookup's suggestions would add state to save a call that a larger `limit` already covers. Narrowing the term is the honest instruction, and the lookup reads the term's whole answer so genuine truncation is still disclosed.

**The cap is 200 and `limit` has no input maximum.** A `limit` above the cap has one reading, so it is served at 200 and the guidance names the limit asked for when matches were cut, instead of an `invalid_arguments` rejection. The schema uses `multipleOf(1)` where `.int()` would advertise a `maximum` of 2^53 - 1 for a value the handler clamps. 200 tags cost 13.9 KB of `structuredContent` and 12.1 KB of text (`frozen`, 209 matches), against 7.0 KB and 6.1 KB at 100 and 17.7 KB and 16.5 KB for a 50-row `pasta` search. Reporting "at least N" whenever a lookup returns a full pool was rejected: `e330` fills a 200-suggestion pool with entries that all fail the substring gate, so a one-tag answer would read as truncated. Reading the whole answer makes the count exact instead, below the 2,000 a lookup asks for.

**The live suggestion pool is requested in full, and the exact-term tag ranked first.** Upstream orders a term's suggestions compounds-first: `lentil` answers eight `en:lentil-*` tags with `en:lentils` last, `chickpea` puts `en:chickpeas` fourth of four, and `cheese` puts `en:cheeses` 37th of 69. An E-number term answers the whole 650-tag additive vocabulary, where `en:e314` is 229th. A request sized to `limit + 1` misses the plain tag at small limits, and one sized to 200 misses `en:e314`, so reordering alone cannot reach it; asking for 2,000, above the largest answer measured (1,313, `c` on categories), reads everything a term matches in one request that costs at most about 119 KB, so the substring gate, the ranking, and the match count all see the complete answer. An answer that reached 2,000 would be cut there with nothing flagging it, and its count would be a floor; none has come close. The ranking is an exact equality on the hyphenated slug and its `s`/`es` plurals, stable and live-portion only, so no entry is added or dropped and a compound sharing a word keeps its place. Terms whose plain tag upstream never suggests (`berry`, `tomato`) are unaffected.

**The tag the term names leads the merged list, whichever source supplied it.** Browse row 1 has to be the tag a filter on the same term resolves to, because a caller copies it. Ranking the exact tag within the live portion alone fails that: the embedded block sits ahead of it, so a small `limit` cuts the confirmed tag behind sample entries that merely contain the term. Of 16 terms whose tag the accept rule confirms, 8 missed row 1, among them `nuts` on allergens, where row 1 was `en:peanuts` while an exclusion on `nuts` resolves `en:nuts`. So one function, `confirmedTag`, decides the single entry that `canonicalizeTag`, `resolveLive`, and `search()` all accept, and `search()` moves that entry to the front, adding it when the substring gate missed it. Only that entry moves, so the embedded block otherwise keeps its hand-maintained order ahead of the live portion, which is what keeps the live suggester's E-number noise below the sample's exact matches.

**Ingredients has no offline sample.** Open Food Facts' ingredient vocabulary is open-ended, so a fixed sample would be an arbitrary slice that answers some terms and reads as no match for the rest. The facet resolves only through the live `ingredient` autocomplete, under the same substring rule and accept rule as the other live facets, and so every browse or canonicalization of a value it has not cached spends a taxonomy-budget lookup. The absence is a type, not an empty list: the sample map is keyed by the facets that have one (`SampledFacet`), so no "offline sample (0 entries)" wording can reach a caller. Without a term the facet returns no tags and a notice asking for one, a failed lookup returns no tags and a notice saying the empty list does not mean the term has no tag, and a no-match notice names the singular form ingredient IDs take.

**NOVA group and Nutri-Score tag IDs are bare, not `en:`-prefixed.** `off_browse_taxonomy` emitted `en:1`–`en:4` while `off_search_products.nova_group` accepts `"1"`–`"4"`, so passing the advertised ID back was a hard validation failure. Fixing it at the source rather than relaxing the enum: upstream tolerance is not uniform, and normalizing on input would have to land before `buildTextSearchQuery`. On the tag backend both forms return the same 136,019 matches, but on the text backend `nova_group:en:1` is live-verified answering zero hits flagged `is_count_exact: true` — a confident false "no products" rather than an error. Bare digits also match the bare grade letters `nutrition_grades` already emitted.

**`off_compare_products` keeps partial results in output, not errors.** When 3 of 5 barcodes resolve and 2 are not found, the caller gets a comparison table for the 3 found products plus a `not_found` list. Throwing when any product is missing would break "compare this grocery basket" workflows where some products are regional or recent.

**A barcode whose fetch failed goes in `failed`, never in `not_found`.** The two are opposite claims: `not_found` asserts Open Food Facts answered and holds no record, while a failed fetch means the barcode was never checked. Classification is by how the promise settled, never by error text — the service resolves `null` only for a genuine not-found, so any rejection is a failure. Failures stay per-barcode instead of aborting the call, so a mixed batch keeps the rows that resolved; the framework reads a non-empty `failed` array as partial success and records it on the tool span.

**Failures leave the service already carrying their contract `reason` and recovery hint.** Handlers stay pure — the service passes `{ reason, ...ctx.recoveryFor(reason) }` on every throw, so `data.reason` and `data.recovery.hint` reach both client surfaces with no handler-side try/catch. Reasons resolve from the error's `JsonRpcErrorCode` and the framework's `data.retryable` flag, never from message text.

**The HTTP status decides retryability; the body only shapes the message.** Every upstream 4xx except 429 (`rate_limited`) and 408/425 (`upstream_timeout`), and any status the framework flags `data.retryable: false` — today only 501 Not Implemented — is `upstream_rejected`: non-retryable and sent once. A request the upstream refuses will be refused again, so retrying only aims more traffic at a backend already saying no. Every other 5xx, and an HTML page served with a 2xx, stays `upstream_error` and is retried. `data.status` disambiguates which status it was, and the upstream's own explanation (a `detail`, or the `description` of a 2.x `errors` entry) is surfaced in the message. A rendered error page is summarized according to the reason the status already settled: served with a refusal it reads as a refusal, and only with a retryable failure is it attributed to load. Product Opener answers every anonymous search page past 10 with a 401 and a rendered page, and blaming load there told the caller to wait out a refusal that cannot change. The 501 needs the flag read explicitly: it keeps the transient `ServiceUnavailable` code, and the published-field allowlist dropped the flag, so it was re-flagged retryable and sent four times.

**`content[]` is escaped per context; `structuredContent` stays raw.** Open Food Facts is contributor-edited, so every product name, ingredient string, brand, grade, and tag ID rendered into the text surface sits outside this server's trust boundary — and the metacharacters are already in real records (`lécithines [SOJA)` on barcode 3017620422003). Interpolated straight into Markdown, such a value changes the structure of the document rather than being displayed in it, so text the server presents as data can present itself as instructions to the reading agent. `src/utils/markdown.ts` holds one escaper per context — inline value, table cell, code fence, inline code span, bare URL — and every formatter routes untrusted values through the one for the site they land on. Line-break handling is the load-bearing part everywhere, since it is the only character that opens a new block, which is why it applies even to values that look harmless. Raw values belong in `structuredContent` and are never escaped there: a parity test asserts the escaped rendering and the raw structured value together. `ctx.enrich` notices are out of scope in the opposite direction — an enrichment string reaches both surfaces as the same value, so escaping one would break that parity, and the fix there is to keep untrusted text out of notice prose.

**Budgets count upstream requests, not logical operations.** Each limiter charges a slot per attempt from inside the retry boundary, so the configured per-minute number is the number of requests Open Food Facts can see from this server. Charging once per call let the framework's four-attempt default fund four requests per slot — a ten-barcode comparison against a failing upstream sent 40 product reads against a published ceiling of 15/min, and the limiter recorded ten. When a budget runs out mid-sequence the retries stop and the caller gets the declared `rate_limited` failure with a `retryAfter` computed from the oldest timestamp still in the window. That refusal stays `retryable: true` on the wire — waiting and retrying is the right move for the caller — so it opts out of `withRetry` by type instead: it is its own error class, and the retry predicate fails fast on it. Reading `data.retryable` there instead would have flipped the flag the caller depends on, and leaving it in the transient set would have made the handler sleep the whole window and try again rather than returning.

**The public error contract publishes an allowlist, never the fetch error's whole `data`.** `error.data` carries `status`, `retryAfter` when the upstream sent one it can read (in whole seconds, the unit the local budget refusals use: delta-seconds as given, an HTTP-date as the seconds left, anything else dropped), `retryAttempts`, `operation`, the per-call context of the tool that failed (`barcode`, or `page`/`page_size`, or `taxonomy_name`/`term`), plus the `reason`, `retryable`, and `recovery.hint` added at the throw site. The framework's fetch helper attaches more than that — it captures the response body as both `body` and its legacy alias `responseBody`, and adds `statusCode`, `statusText`, and `errorSource` — and spreading it put two copies of a rendered Open Food Facts error page into `structuredContent.error.data`, more than half the bytes of the failure, while `content[]` carried one summary sentence. Selecting here keeps the two surfaces saying the same thing and keeps provider markup off both: the upstream's own explanation still reaches the message, as a fixed summary when the body is a rendered page and otherwise as the body's own text — search-a-licious's `detail` string or `errors` descriptions, or a snippet of anything else — each bounded to 200 characters with its markup stripped.

**Each backend's page bound is enforced before the request.** `search.openfoodfacts.org` rejects `page * page_size > 10000` with an HTTP 422, and `/api/v2/search` answers any page past 10 from a client that is not logged in with an HTTP 401 and a rendered page, whatever the `page_size` and however few products match (see "Search"). Checking both in the handler turns a request that cannot succeed into a `page_out_of_range` failure naming the highest reachable page, with no upstream call. `last_page`, the exhausted-page notice, and the truncation guidance all use the same reachable bound — `min(10, page count)` on the live tag path, and the page count capped at `⌊10000 / page_size⌋` on the text path and when the mirror served it — so none of them names a page the pre-check would refuse. Logging in to lift the tag-path bound was not considered: the server is keyless by design, and the text path already serves deep result sets.

**An over-cap `page_size` is served at 100, not refused.** The cap is Open Food Facts' own `/api/v2/search` page maximum. A `page_size` above 100 has one obvious reading, so it is sent as 100 and every page computation — the bounds, `last_page`, the truncation `cap` — runs at that served size, echoed as `page_size`. `page` counts pages of 100, so repeating one over-cap value pages contiguously (page 2 at `page_size` 200 is results 101–200), and the `page_size_capped` enrichment names the next page and the results it holds whenever that page can be requested. `page_size` has no upper bound, because a larger value has the same one reading at any size; the schema uses `multipleOf(1)` where `.int()` would advertise a `maximum` of 2^53 - 1 for a value the handler clamps. `multipleOf` tolerates float noise, so `20.000000000000004` passes it, and a `Number.isInteger` refine, invisible to tools/list, refuses that; it runs only where `multipleOf` passed, so a plain fraction reports one issue. The result window still bounds `page`, since no backend serves past result 10,000. Predicate inputs — `labels_tag`, the exclusion lists, `nutrient_filters`, `query` words, a page past the reachable depth — keep rejecting, because dropping entries would change the query rather than shorten the answer.

**`truncated` means matches exist beyond this page.** It is set when the total is a lower bound or when `page × page_size` (served) is below the total, keyed on the page's offset rather than on the rows it delivered: a row left off for an unservable code shortens a page without leaving anything beyond it, and a page whose every row was left off is still truncated when matches lie beyond it. Comparing the total with the current page's row count instead would mark the final page of every multi-page result as truncated. A genuine final page carries no truncation fields and no paging notice, like a single-page result, and `last_page` equals `page` there. The last reachable page of a bound-cut result set keeps its truncation and its "that is as deep as … paginates" guidance.

**`format()` renders what `structuredContent` carries — no formatter-local slicing.** The text surface previously capped parsed ingredients at 20 and category tags at 5 (3 in search), rendered completeness only as a rounded percentage, and dropped `vegan`/`vegetarian` when the value was `maybe`. None of it reduced the payload — the full arrays and exact scalars were already in `structuredContent` — so the caps bought nothing and left text-only clients (Claude Desktop) with a quietly incomplete record that no follow-up call could complete, since re-calling returns the same trimmed text. Two of the losses were silent misreadings rather than omissions: `79%` is indistinguishable from an exact `0.79` when the value is `0.7875`, and `maybe` is a real OFF verdict ("depends on sourcing") that rendered identically to no verdict at all. These are capped-*list* cases in name only; the honest fix is full parity, and the `fields` input already exists for callers who want a smaller response. Outline-on-overflow does not apply — it addresses one document-shaped record too large to inline, and a product record is neither document-shaped nor near the budget: the heaviest parsed-ingredient tree in a 616-product survey (5000159541374, 120 top-level and 179 total entries) measures 14.0 KB of `structuredContent` and 9.2 KB of text for the name and ingredients alone — roughly 18 KB and 13 KB with the rest of a full record — against a 24 KB outline budget, and the `fields` input already gives a caller who wants less a way to ask for it.

**Sub-ingredients nest under their parent, written out three levels deep.** Open Food Facts nests them in `ingredients[].ingredients` (wheat flour under "cereal", palm oil under "vegetable oils", milk under cheddar under a seasoning), and a diet or allergy check often needs exactly those. Each entry carries its children as an `ingredients` array of the same entry shape, rendered indented under the parent in `content[]`; the top-level list keeps its length, order, and values. A nested `percent_estimate` is a share of the whole product, not of its parent — a parent's estimate equals the sum of its children's in 1,027 of 1,060 surveyed parents — so the schema says so, and a flattened list would double-count. The schema is inlined rather than self-referential, because a recursive Zod schema overflows the definition linter's stack and emits `$defs`/`$ref`; three levels is the deepest nesting observed (616 products: 228 flat, 321 two levels, 67 three, none deeper). Upstream permits more, so an entry below the third level is listed at the third, directly after its ancestor, in pre-order — only parentage is flattened and nothing is dropped. A flat list with parent references was rejected: it changes the meaning of the existing array, needs index paths because IDs repeat within a tree (`en:salt` under two cheeses), and runs 20–45% larger.

**A clipped hit count is labelled, never rounded off or hidden.** The text backend stops counting at 10,000 and reports `is_count_exact: false` when it does; `total_is_lower_bound` carries that straight through to the caller, and `format()` renders the figure as `10000+`. The alternative — presenting the ceiling as an exact total — makes every broad query report the same fabricated number, and made the pagination guidance derive a precise page count from it. Detection reads the upstream flag rather than comparing the count against `TEXT_SEARCH_RESULT_WINDOW`: the page-depth limit and the hit-counting limit are separate limits that sit at the same number today, and only the backend knows when it stopped counting.

**Nutrient constraints are a structured input served by one backend, not a raw query string.** The caller supplies `{ nutrient, operator, value }` from two closed enums and a validated number, so no caller-authored text can enter the Lucene `q` as syntax and the supported set cannot drift past the nine fields verified indexed. A separate nutrient-search tool would have duplicated the search, pagination, and result schemas. Client-side filtering as the means of serving a constraint was rejected, because it produces false totals and incomplete pages, since it can only inspect the rows already returned; the nutrient clause is the filter, sent as given (see the decision after next). Because only the text backend applies the comparisons, a request carrying one routes there with or without `query` and inherits that path's properties — the result window, the counting ceiling, and the lagging index — which is why the `page_out_of_range` pre-check keys on the routing decision rather than on `query`. Sending `/api/v2/search` its own documented comparison parameters and keeping tag-only routing was rejected on measurement: they are ignored, so the tool would return unfiltered rows under an unfiltered total while appearing to filter.

**A nutrient-filtered row shows the index's value, not the live one.** The filter runs against the lagging index, so a row can match on a value the current record no longer holds (`7771711000483`: 3.85 g indexed, 17.5 g live). Each row carries `indexed_nutriments` — the constrained keys only, keyed as `off_get_product` keys them — and the `text_index_snapshot` note echoes the constraints and names that field, so the caller can see why a product matched and compare it against `off_get_product`; the note also says the constraints were compared as given and reach only products whose index entry carries each constrained nutrient. Fetching every candidate's live record was rejected: it spends the product budget per row and returns values that cannot explain a snapshot match. Replacing the indexed values with live ones would hide the mismatch and leave totals counting products the live values exclude. Unconstrained nutrients stay off the rows; the summary row is for triage.

**Nutrient bounds are sent as given, and the index's coverage is disclosed rather than worked around.** The 2.x index maps all nine nutrients as `float`, so a clause compares the decimal it names (`sugars gt 3.5` excludes 3.5 and keeps 3.6) and the range the index answers is the constraint itself. Nothing refines it: no widened bound, no client-side row check, no count of rows left off a page, and `total`, `last_page`, and paging are the index's own. What the index cannot do is reach a record whose entry carries no value for the nutrient, which many do, including records whose live read has nutrition figures (47 of 1,447 `en:skyrs`, 671 of 5,026 `en:ketchup`, measured 2026-11-24). No other backend applies the comparisons, so the gap stays, and the `nutrient_filters` description and the `text_index_snapshot` note say a constraint reaches only products whose entry carries the nutrient, and the description adds that an empty result does not show none exists.

**Every read is bounded by one total deadline, and an expiry is `upstream_timeout`.** The 15 s per-attempt timeout bounds one attempt only, so against a hung upstream a product read would hold for about 64 s and a search for about 67 s, past the 60 s default request timeout of MCP SDK clients, and the caller would give up before a typed failure reached it. A search that canonicalizes a tag runs a lookup ladder and then the search ladder, doubling that. The budgets are 35 s for a product or search read and 20 s for a lookup, so one caller's longest chain (parallel lookups, then one search) settles at 55 s, under 60 s. That holds for a caller that joined a lookup whose starter cancelled: it restarts the lookup with what is left of its own 20 s, not a fresh 20 s, which would let one cancel push the chain past 60 s. Answering it `lookup_failed` instead would refuse an exclusion it still had time to confirm, and detaching the shared lookup from its starter's signal would need a substituted context and per-caller races for a case that needs a cancel and a hung upstream together. Expiry is mapped to the declared `upstream_timeout` in one wrapper rather than declaring the framework's `retry_deadline_exceeded` on four tools, and a read whose last finished attempt answered 429 reports the 429, because a limit is waited out and an outage is not. A caller abort stays a cancellation.

**A `timed_out` answer is refused, not read.** Elasticsearch returns it as an HTTP 200 with a complete envelope, so no shape check catches it, and a page or count read from it is wrong. It is raised inside the retry boundary as the retryable `upstream_timeout`, like an `errors` envelope.

**A connection dropped mid-body is the retryable `upstream_error`, mapped in `parseJsonBody`.** `fetchWithTimeout` classifies every failure of a 2xx body stream as an `McpError`: a stall or a caller abort keeps its own path, and a connection closed part-way through the body, with neither signal behind it, arrives as a `ServiceUnavailable` network error whose `data.errorSource` is `FetchNetworkErrorWrapper`. Only that one is mapped to the dropped-connection message; anything else a body read rejects with goes through `toContractError`. The mapping sits at the two body reads rather than at `toContractError`'s first line, because the same network error raised there, before the headers, is no dropped answer, and that line also passes programming errors from building a request, which must not read as a dropped connection. The runtime's text stays in `cause`, since it names options a caller cannot use.

**An empty page inside a positive result set is an exhausted page, not a zero-match search.** Both backends answer a page past the end with an ordinary HTTP 200 — the text path with `hits: []` beside a positive `count`, the tag path with `products: []` and `page_count: 0` — so nothing upstream separates the two, and keying the empty branch on `products.length` alone reported "no products found" beside a positive total and told the caller to broaden filters that were matching products. The handler and `format()` both split on `total === 0`: zero keeps the broaden / check-tag-IDs guidance, a positive total names the requested page and the deepest page that holds results. That bound is the same `reachablePages` the truncation branch computes, so it can never name a page the `page_out_of_range` pre-check would refuse; when matches lie past it, as on a page past 10 that the live count answers for a brand the mirror holds no product under, the bound also says how many of the matches it reaches ("the first 500 of the 550 matches"). It is withheld entirely when the total is a lower bound, since dividing a count the backend stopped incrementing would present its ceiling as a measurement. `last_page` exists in `output` because `format()` sees only the fields it is handed and cannot otherwise name a page number that agrees with `structuredContent`.

**Text-search freshness is disclosed at runtime, and dated by a bounded probe.** The text index lags the live database, so the same filters answer differently depending on whether free text is present. The disclosure rides an `enrichment` field, `text_index_snapshot`, which reaches `structuredContent` and the `content[]` trailer on every response the text backend answered; when the service holds the index's date, the note names it and says a product contributed since is missing and one edited since is matched and shown as it was then, and the response carries it as `text_index_as_of` (rendered as `**Text index as of:**` under Source), and the empty-result notice adds that an empty text result does not settle whether a matching product has been contributed — naming what does reach one: `off_get_product` by barcode, and the same tag filters without `query` (or tag filters in place of a `query`-only search). Neither text advises dropping `query` when none was sent: a nutrient-only search stays on the text index whatever is dropped, so both say that instead. No runtime string carries a literal date: the date is read from the index, never written into a string, because the index moves whenever Open Food Facts reloads it and a literal would be a claim nothing re-checks. Without a date (the probe failed, is backing off, or found no spare search slot) the note says only that a recently contributed product can be missing. `total_is_lower_bound` keeps its one meaning from the clipped-count note above and is not overloaded to signal staleness. Routing text queries to `/cgi/search.pl` was rejected: it returns current data but answered the majority of probes with HTML error pages, refused deep pages with HTTP 401, and took 5–22 s per query — trading a disclosed lag for an undisclosed failure rate.

**The text index's date comes from one cached probe, bounded so it never takes the last search slot.** The index publishes no timestamp, but its newest record does carry one, so a text search dates the lag by asking for it: one `POST /search` with no `q`, sorted newest edit first, one hit, `last_modified_t` only. A date lets a caller judge whether a missing product is plausibly newer than the index, which "lags" alone does not. The cost is bounded on every side. The probe has its own 3 s timeout (`TEXT_INDEX_PROBE_TIMEOUT_MS`) across request and body, on its own timer rather than any caller's signal, since every search waiting on it shares it. One probe runs at a time (single flight), however many searches wait. The date is reused for 6 h (`TEXT_INDEX_DATE_TTL_MS`), so steady traffic sends about four probes a day, and a failed probe backs off 15 min (`TEXT_INDEX_PROBE_BACKOFF_MS`), during which answers go undated rather than retrying into an outage. It takes a search slot only while two or more are free (`tryAcquireSpare`), so a probe never takes the last slot of the 10-a-minute budget and a caller's own search can still follow; with fewer spare, the answer goes out undated. The slot it takes still counts against that budget for the next 60 s, so a search within that time can meet `rate_limited` one request sooner; the probe spends at most one request per 6 h, or one per 15 min while it keeps failing. It is asked on a search's first attempt only, sent beside the search after the search has claimed its own slot, and waited on only once the search has answered, so it never delays a failing search, and a probe that ends within 3 s of the first attempt's start keeps the call inside the read's own deadline. A caller cancelled while waiting ends at once (`untilCancelled`) and the probe runs on for the others. A failed probe is logged and never fails a search. Reading the date from each search's own hits was rejected: a page holds an arbitrary slice, not the newest record, and sorting every search by recency would change its ranking.

**`sort_by` applies on both paths, in each backend's spelling.** search-a-licious sorts descending on a `-` prefix and ascending on the bare field name, while `/api/v2/search` reads the bare value as descending. The service adds the prefix on the text path so one enum value means one thing to the caller, and every value stays "newest or highest first". Ascending order is not exposed: all four fields answer "most" or "newest" questions, so the reverse would double the enum to serve no asked-for question.

**Text search sends 31 language codes and `main`, by POST.** With no `langs` the backend searches English subfields only, so a product named only in French, Russian, or Portuguese is invisible to `query` (`шоколад` 359 hits against 870, `bolacha` 222 at six languages against 660 at 30, `confiture abricot` 805 against 10,000+). The 2.x index holds name fields for 181 languages and `main`, the name in the product's own main language, which reaches a product by its own name in any other (`czekolada` 108 on the 31 codes, 370 with `main` added). The 31 codes are the languages the 1.x index analyzed, so every name those codes reach stays reachable, and each code costs two fields per query word, so the other 150 stay unsent. The list is a constant, not a caller input, because callers rarely know which language a record was entered in. `POST /search` takes the same parameters as a JSON body and returns the same hits for the same `q`, `sort_by`, `page`, `page_size`, and `fields`, and keeps the query out of the URL.

**A text query is its words alone, and 2.x requires every one.** The 2.x backend requires each space-separated bare word and leaves stop words out of the requirement, so `total` counts the products matching every word and the service sends the words alone (`confiture de fraise` and `confiture fraise` both 1,956, live 2026-11-24). A word joined to another by punctuation is one term to it, matched by any one of the parts its analyzers split it into (`coca-cola` 10,000+ against `coca cola` 2,969), so the service sends the words apart: a word is what the analyzer calls one, extracted with the grammar probed live (runs of letters, marks, digits, and `_`, joined across a single `'`, `’`, or `.`, or a `,` between two digits, so `l'eau`, `u.s.`, `a_b`, and `1,5` stay one word each). The query is lowercased so a caller's `AND`/`OR`/`NOT` reads as a word, since only the uppercase forms are operators to the parser, and escaped so it cannot inject a field clause. A query that holds no word is sent as typed, which matches no product (`%%%` 0), where sending nothing would match every one. The words reach product and generic names only: the category, label, and brand fields hold tag IDs no word equals (`hummus` matched 2,643 of the 4,616 `en:hummus` products, live 2026-11-24), so those constraints are the tag filters', and the tool descriptions and the zero-result notice say so. A stop word of any searched language is not required, so a content word that is a stop word in one of them (Spanish `soy`) does not narrow the result, and a tag filter is the way to make that constraint hard. `query` is capped at 24 words because each word costs a clause per name field of every language sent and this server bounds what one query costs the backend (60 words still answered normally, live 2026-11-24).

**Tag inclusions are canonicalized on the text path, and on the tag path while the mirror is ready, best-effort.** The text backend's tag fields are exact-match keywords while `/api/v2/search` canonicalizes the same values, so a value that worked on a tag-only search returned an exact zero once `query` or `nutrient_filters` was added. Each value is resolved before it is quoted, through the taxonomy service (see its canonicalization entry): confirmed IDs only, never a prefix or partial match, so `brands_tag: "nutell"` still matches nothing (#13). The live tag path is left untouched because Product Opener already canonicalizes there; the mirror matches stored tags exactly, so with a ready mirror the tag path's values are canonicalized too (spending the taxonomy budget), and the mirror serves the search only when every value is a vocabulary-confirmed tag and a brand is one it holds products under any key of (next entry), else the search is sent live with each value as given, a brand under `brandLiveIds`. A failed lookup or spent taxonomy budget sends the value normalized instead of failing the search, and the empty-result notice names each value nothing confirmed, the IDs it was sent under, and a failed lookup's cause and any known wait. The text index holds a tag under the ID the text each record was entered as gives it, so a value nothing confirmed goes there under every ID it can take (`taxonomyTextIds`): the ID Product Opener normalizes it to, and, when a whole-string lowercase spells it differently, that lowercase's ID, the two as one quoted OR group. An all-caps value ending in a capital sigma normalizes with `σ` (`EL:ΣΑΛΑΤΕΣ` → `el:σαλατεσ`) while a record typed in lowercase carries `ς` (`el:σαλατες`), so `categories:("el:σαλατεσ" OR "el:σαλατες")` matches a record under either, as a brand's spellings do (next entry). Live 2026-11-24 the index holds `el:` categories ending in a final sigma only under `ς` (`el:*ς` matches 66 records, `el:*σ` none), and `EL:ΧΥΜΌΣ` finds its 2 products only through the `ς` ID; each member of a list that must all apply is its own clause, so one label's two IDs never read as two required labels. A confirmed value goes under its entry's ID alone, and the tag path and mirror never carry the pair. The second ID is derived from the value as given, never stored with the cached resolution. Loud rejection of unconfirmed values was rejected for inclusions: it needs the same lookup, turns an outage of the vocabulary into an outage of search, and would refuse values the index does hold under an ID the autocomplete cannot find by name. Exclusions take the opposite trade (see the exclusion entry), because an unconfirmed exclusion fails silently toward a wrong answer rather than toward an empty one.

**A brand is matched under every key it can be stored under, on every path.** Product Opener stores a brand it does not recognize as typed text on a schema 1004 record (`xx:Красный Октябрь`) and as a slug on an older one (`xx:красный-октябрь`), and a synonym's older records under the synonym's own slug, so a search under any one spelling counts a fragment of the brand's products, and a different fragment on each backend: live 2026-11-24, `Красный Октябрь` counted 7 on the mirror (`xx:красный-октябрь`) and 16 live (`xx:Красный Октябрь`) of 28 records, and `7-Up` 30 on the mirror (`xx:7-up`) and 297 live (`xx:7up`) of 486. The stored form follows each record's schema version, not its save date. So one function, `brandKeys`, computes the brand's keys (its slug and the keys of every name its `taxonomies/brands.txt` entry lists; see the taxonomy service), and every path matches the whole set. The record builder indexes each `brands_tags` value as `brands:xx:<brandKey>` at ingest, the mirror query matches the keys at query time, so every spelling of `Красный Октябрь` counts the same 28 records and `7-Up`, `Seven Up`, and `7up` the same 486, and `Andechser` keeps its 32 beside `andechser-natur`'s 77. A brand is held when any of its keys has postings, and the mirror search sends the held keys as one any-of filter. Live sends the brand as given plus each key as an exact stored tag (`<given>|xx:<key>!`), so a live total only grows, and the text path sends `xx:<given>` plus each key bare and `xx:`-prefixed, with the final-`ς` spelling of a key ending in `σ`. The mirror keys a stored brand at ingest rather than matching its stored text because one brand is stored under several spellings, typed ones in any case included, and a key both sides compute is the one form that meets them all; live compares stored tags exactly, so a typed spelling in another case that no key names stays out of its reach. Routing a brand to the mirror only when held keeps every mirror answer a count of products the copy actually has, and lets live answer the rest instead of reporting a false zero. A brand outside the synonym table matches its own key alone, and an entry matches a whole key, never a substring, so `nutell` still matches nothing (#13).

**Brand keys are computed locally, and the synonym table ships with the package.** `brandKeys` needs the names each brand entry lists, which the static `brands.json` dump omits, so `src/services/taxonomy/brand-synonyms.ts` carries them as generated data from `taxonomies/brands.txt` at a pinned openfoodfacts-server commit (see "Static dumps"). The data is small (195 groups at that commit) and factual brand-name data, like the nutrient and unit tables the package already embeds, and it compiles into `dist/`, which the package and the `.mcpb` already ship, so no data file is added. A synonym added upstream after the pinned commit matches its own key alone until `bun run brands:sync` regenerates the module.

**A page past the live bound for a brand the mirror cannot match is settled by one live count.** A tag-only search past page 10 with a brand the mirror holds no product under, or before a full load has keyed every brand, would read live, which serves no page past 10. The handler sends the same filters live as a count (`page` 1, `page_size` 1). A live total that ends before the requested page starts answers the page empty, with that total, as the mirror would answer a page past its last. A total that reaches into the page is refused as `page_out_of_range` naming the brand and the live total (`data.brand`, `data.live_total`, not retryable), since those products exist and no page here can serve them. A bare refusal on every such page told a caller nothing about whether the brand matched anything; the count answers it for one request. Other unconfirmed values keep their refusal (`data.unconfirmed`), and a brand listed among them carries `reason: 'not_held'`, or `'unindexed'` when no full load has keyed every brand yet.

**Exclusions are sent only as confirmed allergen tags, on both paths.** `exclude_allergens` and `exclude_traces` exist because both backends negate a tag filter natively (`-c` in a Product Opener `*_tags` value, a top-level `-field:"value"` clause on the text path), and screening candidates one `off_get_product` call at a time costs a product read per row and yields no total. A negated value that matches no stored tag does not empty the result the way a wrong inclusion does; it excludes nothing, and the response looks filtered. So each exclusion value runs through `canonicalizeTag` against the allergen vocabulary on both paths, including the tag path, where Product Opener would otherwise canonicalize a typo to a tag nothing carries, and anything short of `vocabulary` is refused as `unrecognized_exclusion` before a search is sent. A singular resolves to its plural tag where the live pool holds one (`en:nut` → `en:nuts`), so the refusal falls on values neither vocabulary confirms. A refusal caused only by failed lookups — an unreachable vocabulary, an Open Food Facts 429, or this server's spent taxonomy budget — is flagged retryable, and its message and hint name each cause and the longest known wait; the 14 major allergens resolve from the offline sample without a lookup. Trace tags are allergen tags upstream (`traces_tags=en:nut` counts the same 12,450 chocolates as `en:nuts`), so traces share the allergen vocabulary.

**An exclusion's coverage gap is disclosed on the response, not only in the description.** Open Food Facts cannot tell a product free of an allergen from one whose allergens were never entered, and an exclusion passes both: of the 26,084 chocolates without nuts on the tag path, 15,936 have no allergen data at all. Every response carrying an exclusion gets an `exclusion_coverage` enrichment on both surfaces naming the gap and the `off_get_product` fields to check, because a caveat that lives only in an input description is easy to miss at the point the results are used.

**`labels_tag` and `ingredients_tag` take a string or an array, all of which apply; the verdict filter is a closed enum.** A single-string `labels_tag` sends exactly the request a lone value always sends; an array ANDs its values, as one comma-joined `labels_tags` on the tag path and one clause per value on the text path. `ingredients_tag` shares the handling (up to 10 values) but is sent only to the text index, as one `ingredients_tags:"en:inulin"` clause per value. A record's `ingredients_tags` carry each ingredient's taxonomy parents too (a record listing carrot also carries `en:vegetable`), so a broad ingredient matches its descendants. The live tag path could filter on ingredients but stops at page 10 and the mirror indexes none, so the search takes the text index's 10,000-result window and its lag, which `text_index_snapshot` says (dropping `ingredients_tag` is what reaches the live database). OR within a tag facet is not offered; the grade inputs are the exception (next decision). `ingredients_analysis_tag` is a `z.enum` of the 12 verdicts in the Open Food Facts `ingredients_analysis` taxonomy, so it needs no canonicalization and a caller cannot send a value that filters nothing.

**`nutrition_grade`, `nova_group`, and `ecoscore_grade` take one grade or an array, matching any of them.** A product carries one grade of each, so all-of on two grades matches nothing and any-of is the only useful multi-value meaning; the descriptions contrast it with `labels_tag`, whose values must all apply. "Nutri-Score B or better" is `["a", "b"]`, one call where one search per grade cost two of the ten searches a minute and left the caller to merge totals, sort orders, and page bounds. Values are deduplicated, a one-element array behaves as the scalar and sends exactly the request the scalar always did, and an empty array is no filter, so the at-least-one-filter check and the live-route test read the normalized values. `ecoscore_grade` takes `a-plus` and `a`–`f`, and `a` does not include `a-plus`.

**A grade input never changes the backend.** A search goes where its other inputs send it, and each backend takes an array its own way: `nutrition_grades_tags=a|b` on `/api/v2/search`, an `(a OR b)` group on the text index, an any-of tag group on the mirror. Moving a tag-only search to the text index for its grade syntax was rejected because that index's grades lag the live records, so a grade filter stays on the backends that read current grades; a text-path search matches the index's grades, and `text_index_snapshot` says the grades it matched and each row shows can differ from `off_get_product`'s. The sentence goes on every text-path search carrying a grade filter, a single grade included, because a lone grade is matched against the index's value the same way. The empty-result echo renders an array as any-of (`nutriscore="a" or "b"`).

**Green-Score is a mirror facet from record version 2, served only once a full load built at that version completes.** The mirror reads `environmental_score_tags`, the field `/api/v2/search` filters on, not the `ecoscore_tags` copy an older record may hold alone. A row built earlier has no Green-Score tag and only a full load rewrites every row, so until the last completed full load is version 2 or later the search reads live, and without the facet a tag-only Green-Score search could only read `/api/v2/search` and stop at page 10. With a ready mirror in that window, a page past 10 is refused as `page_out_of_range` naming `ecoscore_grade` and the reload. Tag-only Green-Score matches the grade Open Food Facts files for France while each row shows the world grade, so a row can show a different letter than the one it matched.

**The barcode pattern is Product Opener's, restricted to digits.** `off_get_product` and `off_compare_products` share `BARCODE_PATTERN` (`^0*[1-9]\d{3,39}$`), which is `is_valid_code` in `lib/ProductOpener/Products.pm` — strip leading zeros, then 4–40 digits — for digit-only input. The earlier `^\d{8,14}$` rejected codes Open Food Facts serves and `off_search_products` returns (`6035215`, stored as `06035215`; `1212`; 15- and 22-digit codes), and accepted 8–14-digit strings with fewer than four significant digits, which upstream answers "no code or invalid code". Non-digits stay rejected although upstream strips them: `3017620422003a` resolves to Nutella there, so accepting it would let a typo return a different product.

**A search row without a servable barcode is dropped in the service.** The row type declares `code: string`, replacing two `as unknown as` casts that let a missing code reach the output as `barcode: ""`, which `off_get_product` rejects. The same holds for a code that fails `BARCODE_PATTERN`: the text index carries 657 eight-character `00000###` codes and 7 thirteen-character `0000000000###` ones, which Product Opener answers "no code or invalid code" (live 2026-09-23), so a row keyed by one has nothing to chain on either. Dropping it before `page_count` is set keeps `page_count` equal to the rows returned on both paths, and every emitted `barcode` passes `off_get_product`'s schema; carrying the row with `barcode` optional was rejected because it widens the advertised output schema and still leaves a row no follow-up call can reach. `total` still counts the dropped rows — it is the upstream's match count, and no local count of refusable codes exists to subtract.

**Text-path field names are the deployed search-a-licious schema's.** The service builds `q` and `fields` against the 2.x Open Food Facts schema (v2.1.0 `data/config/openfoodfacts.yml`), and 2.x refuses a field it does not hold with HTTP 400 instead of answering zero, so a schema change surfaces as `upstream_rejected` whose message carries the `QueryCheckError` description naming the field. That is the sign to re-read the schema and rebuild the clause shapes.

**`additives_tag` combines with every text-path filter.** The 2.x index holds `additives`, so the clause is sent as `additives:"<id>"` after the value is canonicalized like the other text-path tag values, and it combines with `query`, `nutrient_filters`, and `ingredients_tag` instead of the text path refusing the combination.

**`off_browse_taxonomy` is a separate tool, not bundled into `off_search_products`.** Tag vocabulary lookup is an independent need — it's used to build search filters, not as part of executing a search. Keeping it separate maintains clean tool boundaries and allows tag exploration without triggering a search call.

**Field selection via input enum, not open string array.** Restricts to the fields the server actually handles and normalizes, preventing callers from requesting raw OFF fields that the output schema doesn't cover. The enum doubles as documentation of what's available.

**NOVA group as `number` in output, `enum(['1','2','3','4'])` in search input.** Zod coercion converts the input string to the parameter value. The raw nutriments object also embeds `nova-group` as a number, but the typed `nova_group` field is its only home in the output — see the nutrient-coverage note below for why it is excluded from the open nutrient maps.

**Nutriments normalized in the output schema.** The raw OFF nutriments object uses hyphenated keys (`energy-kcal_100g`) that are not valid TypeScript identifiers. Normalization maps to underscore form (`energy_kcal_100g`) and takes the `_100g` and `_serving` variants; `_value` and `_modifier` are dropped as redundant with `_100g`.

**Per-100 figures are stated as per 100 g, or per 100 ml for liquids.** OFF writes a liquid's per-100 ml figures to the same `_100g` keys without density conversion (Coca-Cola Zero Sugar, 0049000042566: `sodium_100g` 0.00986 is 0.035 g per 354.882 ml serving). No field states a row's basis reliably — on 2026-10-13, `nutrition_data_per` read `100ml` on 70 of 121 sampled liquids and `100g` on 50, this drink included, and serving and package units disagreed on 31 of 240 — so every description and heading names both bases (`Nutrition per 100 g / 100 ml`) and no row asserts one. The `*_100g` field names stay: renaming them would break the contract for no gain. Passing `nutrition_data_per` through was rejected because its `100g` on a liquid restates the defect.

**Nutrient coverage is open, not an allowlist.** The macros keep named schema fields, and every other nutrient a read returns lands in `additional_100g` / `additional_serving` keyed by normalized name, `_prepared` keys included. A fixed map silently narrowed a nutrition database to a dozen macronutrients — calcium, iron, cholesterol, trans fat, added sugars, and the vitamins were all present upstream and dropped, so questions the record could answer came back empty with no field subset or follow-up call that would retrieve them. Two constraints make the open map safe:

- **Exclusion is per exact raw key, not per base nutrient**, derived from the named map so the two cannot drift. The named set is asymmetric across suffixes — `saturated-fat_100g` is named while `saturated-fat_serving` is not — so excluding by base name would drop per-serving macros from both surfaces. Each nutrient therefore appears in exactly one place.
- **The unit comes from the nutrient, never from `_unit`.** On legacy records `{nutrient}_unit` is the unit the contributor entered (current records carry the normalized unit there), while `_100g` and `_serving` are normalized, so calcium entered as 120 mg reads `calcium_100g` 0.12 beside `calcium_unit` "mg" — 0.12 g. And no `_prepared` key has a `_unit` sibling at all. The unit therefore mirrors OFF's normalizer: kJ for `energy`, `energy-kj`, and `energy-from-fat` (OFF files the last under g, but its conversion stores kJ), kcal for `energy-kcal`, % vol for `alcohol`, % for `fruits-*`, `collagen-*`, `cocoa`, `whole-grain`, `moisture`, and the `crude-*` constituents, mmol/l for `water-hardness`, none for `ph` and `glycemic-index`, g for everything else, with a `_prepared` key taking its base nutrient's unit. Values are passed through unscaled; converting value and unit together was rejected as a second source of error on a figure already in a known unit. Percent, % vol, and unitless figures are concentrations, so their `_serving` equals `_100g`.

`nova-group` is excluded outright: OFF stores the NOVA processing class inside the nutriments map with an empty unit, and it is already surfaced as the typed `nova_group` field, so passing it through would report the same classification twice.

**Per-serving figures always carry their denominator.** `serving_size` (as printed), `serving_quantity` (parsed), and `serving_quantity_unit` are requested and returned alongside the `_serving` nutriments; `format()` restates the serving size on the per-serving heading and says outright when OFF has recorded none. Per-serving numbers without a serving size cannot be compared across products or converted to or from the per-100 figures. `serving_quantity` is coerced rather than type-tested — OFF returns it as a JSON number for most products and a numeric string for others, so a `typeof === 'number'` guard would drop it for a whole class of records. Its unit is not assumed to be grams: it is millilitres for liquids.

**The serving fields expand as a closed group.** A quantity reads only with its unit and a unit says nothing without its quantity, so `serving_quantity` brings `serving_quantity_unit` and `serving_size`, `serving_quantity_unit` brings `serving_quantity` and `serving_size`, and `nutriments` brings all three. `serving_size` alone expands to nothing: the line it renders claims nothing about a parsed quantity it was not asked for. The expansion is not transitive, so each entry lists its whole set; `nutrient_levels` brings `nutriments` and the group, for its `basis`.

**`nutrient_levels` names the figures it was computed on, from the read's own nutriments.** Open Food Facts computes the levels on its aggregated nutrition set, where prepared figures win, so a record whose read holds only prepared figures has levels that describe the prepared product. `basis` is `prepared` exactly when the read's `nutriments` hold only prepared figures (`holdsOnlyPreparedFigures`, the test that triggers the stored as-sold read), otherwise `as_sold`, and it is decided before the stored set fills the as-sold fields, so a `prepared` verdict can sit beside as-sold figures it disagrees with; the text surface says so on that line. Only the four nutrients Open Food Facts rates are kept (`saturated-fat` keyed `saturated_fat`), a nutrient with no figure has no key, and `{}` or an absent field yields no `nutrient_levels`. `generic_name` is the main-language value: an empty one returns none even when a language variant holds text, as `product_name` does.

**A read speaks for itself about preparation state, and says nothing about the record.** Open Food Facts returns one preparation state of the nutrition per read: a read of prepared figures carries `_prepared` keys and none of the as-sold ones. In 7 of 7 sampled prepared records the as-sold figures were stored, so a statement that the record lacks them is false. Every string that would say so says what the read returned instead: `off_get_product`'s stored-set statement opens "The product read returned only prepared figures", `off_compare_products` prints "This read returned no as-sold figures in the compared columns" for a row with no stored-set read, and the descriptions of `nutriments`, `additional_100g`, and the as-sold compare fields scope their absence wording to the read. Where `stored_as_sold` is present it supersedes this wording, because the stored set was read (next decision). The server `instructions` carry the same exception to "a missing one means not yet recorded".

**A prepared-only product read gets one follow-up read of the record's stored as-sold set (#73).** API v2 and v3.4 serve the aggregated `nutriments`, where prepared wins, so only API v3.5's `fields=nutrition.input_sets` carries the as-sold figures. Reading every product on v3.5 was rejected because it drops `nutriments` and renames fields this server reads (`ecoscore_grade` → `environmental_score_grade`), so the follow-up runs only when the v2 `nutriments` hold `_prepared` figures and no as-sold one (`holdsOnlyPreparedFigures`). Other reads, and a `fields` subset without `nutriments`, send nothing extra. It reads one `as_sold` set, never `estimate` (v2's `nutriments` keeps estimates out too), and never merges sets, so every figure served has one source and one basis: per 100 g / 100 ml first, else a serving of at least 5 g or ml scaled to 100 as Product Opener scales it, then manufacturer, packaging, usda, other. Each nutrient is `value`, else `value_computed`, in the unit the descriptions state (150 mg → 0.15 g); IU, % DV, and other units are left out, and no as-sold per-serving figure is synthesized. The set passes through as stored: a powder whose as-sold energy is below its prepared energy has its sets swapped on the record (`3664346306027` files 148 kcal as sold and 355 prepared), and the server does not correct it. The read is best-effort. It spends the product budget and has a 20 s deadline of its own, so a call settles within 35 + 20 = 55 s; compare starts its follow-ups only after every v2 read has settled, because a v2 retry spends its budget slot late and a follow-up beside it could take that slot first. An unread set (budget refusal, 5xx, 404, malformed envelope, deadline) never fails the call or the row: the product keeps its prepared figures and carries `stored_as_sold: { status: "unread", reason, error }`, shaped like a `failed` entry, while the caller's cancellation still ends the call. `stored_as_sold` exists only when the follow-up ran.

**`off_get_product` keeps prepared figures in the open maps and splits them only when rendering.** The structured values are unchanged: `normalizeNutriments` still files every `_prepared` key under `additional_100g` / `additional_serving`, so "nutrient coverage is open" holds and callers parsing `structuredContent` see no change. `format()` partitions those maps by the `_prepared` suffix, so the as-sold sections keep their keys and order and the prepared figures print under "as prepared" headings, per 100 g / 100 ml and per serving. The per-serving as-sold heading prints only when an as-sold per-serving figure exists, so a prepared-only read has no empty heading. The text prints the structured key (`energy_kcal_prepared`) rather than remapping it to a macro label, which keeps the two surfaces matched. The per-serving prepared section carries a note that Open Food Facts scales those figures from the per-100 figures by `serving_quantity`, often a powder's dry portion rather than the prepared serving, because that figure misleads a reader who sees only the text. The footer reads "Other missing fields" only when the stored set went unread, since the as-sold fields are then missing because of the read; a `read` or `none` set leaves "Missing fields = not yet entered" true of every gap. Each `stored_as_sold` status prints its own "As-sold nutrition (stored set: …)" line stating where the as-sold figures came from.

**`off_compare_products` reads prepared figures into a `prepared` object, from `*_prepared_100g` keys only.** One `NUTRITION_COLUMNS` list drives the row type, the reads, the output schema, and both tables, so the as-sold and prepared shapes cannot drift, and a ninth column such as carbohydrates is one entry. Nothing is derived: a prepared kcal is never computed from kJ, and a prepared figure never fills an as-sold field. `prepared` exists only when a read carries a column figure, so `_prepared_serving` alone, or kJ alone, yields no object. A mixed read, with both states, is 0 of 21 sampled live records.

**Table membership: as sold lists rows with no `prepared`, with any as-sold figure, or with a stored set read, and as prepared lists rows with `prepared`.** A row carrying both appears in both, or `content[]` would drop figures `structuredContent` carries. A prepared-only row leaves the as-sold table, since its N/A cells would sit under a footer reading "not yet entered" for a record that holds those figures on a state this read did not return; a line names such rows and says the read returned no as-sold figures in the compared columns. A row whose stored set was read appears in both, even when that set fills none of the eight columns, since its N/A cells are then true of the stored set the read reached; rows with `stored_as_sold` `read`, `none`, or `unread` are each named in a line of their own, and `unread` rows list their `reason` and `error`. Each table is omitted when it has no rows. The footer is scoped, not removed, when an as-prepared table prints: `"N/A" outside the "as prepared" table = not yet entered`, since Scores keeps its N/A even where no as-sold table prints; with no as-prepared table it is unchanged. The as-prepared table has its own N/A wording ("no prepared figure in this read"). A read whose prepared keys miss all eight columns has no `prepared` object, so it stays in the as-sold table under "not yet entered"; no sampled record does this, and fixing it needs a new output signal.

**The local export mirror is opt-in, and the live path stays the baseline (#79).** Open Food Facts bans an IP that exceeds its published read limits and refuses a tag search past page 10, so a deployment that wants deep tag pages, exact totals, and barcode reads that spend no budget needs its own copy. `OFF_MIRROR_PATH` unset leaves every call, test, and manifest as it was, and the serving process only reads the store: every write runs in a `mirror:*` script or the scheduled job's child process, where a page's write transaction cannot block a request. No npm-facing manifest gains the variable, because the scripts resolve `@/` aliases that exist only in a checkout and the Docker image.

**The mirror's indexes are built after a full load, not when the store opens.** Migration 1 creates the tables and triggers on an empty file, migration 2 adds two columns to the one-row `mirror_load`, and no migration builds an index: one built over a populated table when a process opens the store blocks the serving process for minutes. The sort indexes (one per `sort_by` key, plus `products_code_sort_keys`) come from the sync process, which a reader keeps reading through under WAL: a full load builds them after its sweep and before the checkpoint is set, one sorted pass each, and any run on a loaded store first builds one it lacks. Maintained through the ingest instead, they slow it and come out larger.

**The serving store's open waits at most 250 ms on a sync, and only `mirror:init` creates the store.** The open still writes (the framework's schema statements end in an `INSERT OR IGNORE` of the sync-state row, and it runs any migration the store has not reached, such as migration 2's two `ALTER`s on a store built before it), so it queues behind a sync's write transaction, and SQLite waits synchronously: every caller of the process waits with it. Under the framework's 5 s an open that met a long hold, such as the sort index builds above, held the process 5.2 s per call, and a failed open is retried by the next call rather than cached. Page transactions held the lock 0.32–0.54 s on a store of records twice the export's average size, so 250 ms lets most opens that meet one succeed and gives up on the rest in about 0.29 s, after which the call reads live. Once open, reads never wait on a writer under WAL (0.1 ms under a held write lock). The sync processes and scripts keep 5 s, so one started during a sync waits out a page transaction and is refused by name (`mirror_lock_held`), not by a lock error. One that meets a longer hold, such as an index build, exits naming the sync that holds the lock, read from the lease row through a connection that runs no schema statement: it writes nothing, so under WAL it reads past the lock the store's own open queues behind. A path naming no file is left alone until it exists: an open there creates the file and its directories, so a mistyped path or an unmounted volume would gain an empty store while every call read live with no warning. The serving process checks the path on every call, not only before it first builds the store, because a failed open is retried by the next call and the file can be gone by then; the check is one `existsSync`, about 1 µs on a local disk. A refresh checks it before opening anything and is refused as `mirror_not_initialized`, the same refusal as a store whose first load never completed.

**A sync writes only while it holds the lease.** The framework runner writes its sync state from its own cursor and checkpoint after every page and again when its run fails. A run whose lease another process reclaimed would then overwrite the reclaiming run's state, moving a completed load's checkpoint back and leaving a resumable cursor that sends the next refresh into a full reload. The store the runner gets checks the lease row before each page and state write and throws `mirror_lock_lost` when it is not the run's own. It reads the row rather than trusting the heartbeat, because a holder can reach a write before its heartbeat timer runs: a full load's last sort index build, a synchronous stretch, is followed by its final page and state writes with no turn of the event loop between.

**A tag search picks its count and its page cut by cost.** Its matches are a stream of codes in code order, led by the rarest include's postings. A filter whose postings cost no more to read whole than to seek once per posting of that lead list (`POSTINGS_PER_SEEK` postings read per seek) is merged into the stream, SQLite reading each merged list once in code order and combining them with `INTERSECT` and `EXCEPT`; every other filter is sought, one `product_tags` primary-key seek per streamed code. The total counts that stream or, with at most one include, that include's postings (every product, with none) less the union of the exclusions' postings within them, whichever reads less. The page is then cut whichever way is cheaper: a walk of the sort key's index in search order (from the end, for a page nearer the end), seeking every filter's postings for each product it passes, or the stream itself, each match's sort key read from `products_code_sort_keys` (from the product row on a store that lacks it) and ordered in a temporary B-tree. A walk costs what precedes the page, and the postings cut what its stream reads plus `MATCH_COST` per match, so a rare tag is cheap by postings at any depth and a common tag's first pages are cheap by walk; `planCut` compares the two estimates in sort-index entries. A fixed plan would be slow for one of the two shapes. Only the page's own documents are read.

An any-of list of tags (a grade input's values) is never merged into the `INTERSECT` chain: read as one term its postings arrive in code order only tag by tag, and merging it plans a temporary B-tree sort. It is either the driving include, a `UNION` of single-value selects, or sought per row with `tag_id IN (…)`. An exclusion list is one exclusion per value. An exact any-of total has to count the `UNION`, while a single-value total is read straight from the postings count, so a broad list with nothing else narrowing it costs more than a single grade: measured 23 ms for a pair matching 120k products and 91 ms for a five-grade list matching 300k, on a 300k-product synthetic store, about 0.19 µs per match. A single-value search runs the single-tag statements, with no list machinery in them.

**A mirror-served tag search reaches only its first 10,000 results.** Mirror reads are synchronous SQLite calls on the serving process, so the work one page costs is time every other caller of a hosted deployment waits. The window bounds it: a `page * page_size` past `MIRROR_SEARCH_RESULT_WINDOW` is refused as `page_out_of_range`, by the handler once every value is confirmed and by the service before its store runs the search, so neither runs a page past the window. It is the text path's size, so a caller meets one depth on both backends that page deep, but it is this server's own bound, kept apart from `TEXT_SEARCH_RESULT_WINDOW` so either can move without the other. `last_page` and the truncation guidance cap at it as they do at the text window. With no ready mirror, or on a store error, the search reads live and the page-10 bound applies.

**Mirror order follows the stored sort values, and the response says so.** The mirror orders by `popularity_key` (the default, as Product Opener applies when given no `sort_by`) and `unique_scans_n` as stored with each record, while a live search ranks by its current scan counts, so those orders can differ page for page; the timestamps sort alike. Product Opener's scan updates move a record's `last_updated_t`, never its `last_modified_t`, so no delta carries them: the stored scan values are as old as the record's last edit or the last full reload. The mirror makes no attempt to reproduce the live ranking, so `mirror_snapshot` names the difference rather than claiming a live order.

**The mirror is fully reloaded every 30 days, because deltas carry no deletions and no recomputed values.** A delta lists the products whose `last_modified_t` falls in its window, so it never carries a removed product or a value Open Food Facts recomputes without an edit. Only a full load, whose sweep deletes every row the new export did not stamp and which rewrites every row from the export, drops a removed barcode and brings the recomputed values. A refresh therefore starts a full load when the last one was built by an older record builder (`MIRROR_RECORD_VERSION`), is 30 days old, or is no longer bridgeable by the listed deltas; a refresh never makes the first load, which is the operator's to start with `mirror:init`. The version a completed load records is the lowest that built any of its rows: a load resumed under a newer builder records the older version, so the next refresh reloads it rather than passing a version gate with rows missing their keys. A deploy that raises the version (4 added brand keys) starts a full reload with reason `record_version`, and a search carrying `brands_tag` reads live until that load completes.

**Recomputed values are disclosed, not refreshed.** No public feed carries a recompute: Product Opener's batch runs move only `last_updated_t`, the deltas select by `last_modified_t`, and only the full export carries the result. A daily full reload (a 13.4 GB download, 1 h 48 min end to end, about 27 GB peak disk) is out of proportion, and reading computed fields live on a mirror read would spend the product rate budget the mirror exists to save while tag-only searches still match stored grades. So every `mirror_snapshot` bounds computed values by the record's last edit or the last full reload, whichever is later, says a product removed since that reload can still be shown, and, on a search, says the filters matched the stored values, computed ones included. The two readings stay separate: `mirror_as_of` covers contributor edits and keeps its meaning, and the reload cadence and delta handling are unchanged.

**A refresh never reloads an export identical to the one already loaded.** `mirror_load` records the strong ETag of the export each full load read. Before a reload due for age or a gap, the refresh reads the export's current ETag with one HEAD request (the same User-Agent, and the same stop on any non-2xx, as every other request), and skips the reload when it matches: the same export removes no product the last load kept, and it leaves a gap where it is, because an export older than the oldest listed delta stays older on every read. Without the check, an export that stopped regenerating would be downloaded and ingested again on every three-hour run, about 1.5 h and 13.4 GB each. A skipped reload logs one warning naming the age or the gap, applies the deltas that continue from the checkpoint up to any gap, and keeps serving. A changed ETag reloads; so does a newer record builder, whatever the export, and a load recorded before the store kept ETags.

**A feed line that is not valid JSON, or runs past 16 MiB, is skipped and counted.** It is a per-record failure in otherwise valid upstream content: fetching the export or the delta again brings the same line back, so stopping on it would fail every refresh at that line (a full load keeps its download and resumes at the line) and freeze `mirror_as_of`. The line splitter drops an oversize line's bytes as they stream, holding at most 16 MiB of one line. Each skip is logged with its feed and line number, never its content; the count reaches the sync report and the refresh job's summary, and, for the last full load, `mirror_load.skipped_lines` and `mirror:status`. A resumed load carries its count in the cursor, so a line is counted once however often the load is interrupted. A corrupt download (a zlib error, a short body, a range mismatch) still stops the load and is downloaded again, and so does an export whose every line is skipped or builds no product (see the next entry).

**A full load that stamped no product stops before its sweep (#82).** The sweep deletes every row whose generation is below the load's, so a well-formed export that builds nothing (empty, blank, every line skipped, or no line with a usable `code`) would empty the store and complete with an as-of of 1970, sending every read live. The load is refused as `export_no_products` instead, with its rows, `mirror_load` row, and checkpoint untouched, the download deleted, and the cursor sent back to the download, so the next run fetches the export again rather than skipping it as unchanged, as after `export_corrupt`. Whether anything was stamped is asked of the store (a row of the load's generation), not counted in the cursor: a load resumed after an earlier run stamped its products, or from a cursor an earlier build wrote without such a count, is never refused. The check runs on every entry to the sweep, a resumed sweep included. Zero is the bound because no legitimate export produces it; a short export completes, since telling it from a legitimate one needs a shrink threshold no export has been measured against.

**While a full load runs, its as-of falls to what the rows it has stamped can vouch for (#81).** A reload rewrites each product to the export's version, which can predate the last applied delta, while the deltas past the export restore those edits only once the load completes. Citing the last delta's end through the ingest and sweep would name a time newer than the data behind the answer. So, over a loaded store, the as-of is the older of the one the run began with and the newest `last_modified_t` among the rows the load has stamped, encoded under the load's generation so the runner accepts it below the deltas. A drop is a records-empty page of its own, committed before the rows it covers, because the runner commits a page's rows before its checkpoint; a rise rides the rows' own page. A resumed run makes the same move before it reads on, from the newest change its cursor records, so a load stopped by an earlier release that kept citing its starting as-of is corrected before the rest of its ingest or its sweep. The run then starts from the lowered as-of, as one whose checkpoint a stopped run already lowered does: a row stamped from an export that changed upstream before the load rewrote it reflects only that export. Either way the as-of never exceeds a time every row reflects: an unstamped row reflects the run's starting as-of, a stamped one its export, whose newest change is at least the newest the load has stamped. A load that stamps nothing, and a first load, which serves nothing, move nothing. Moving the as-of back at the load's start was rejected: nothing then bounds the new export from below, and the previous export's as-of, the only safe bound, is not stored and is up to 30 days old.

**A store error falls through to a live read.** The mirror is a faster path to data the live API can still answer, so a failing store (a read that throws, or a stored nutrition-sets value that is not a list) is logged, without the stored document, and the call is served live with `source: "off_api"`, never failed. The caller's cancellation is rethrown instead. A mirror that is configured but not ready (no completed load, or zero products) reads as no mirror.

**The mirror serves a search only when it can match every value as stored.** It matches stored tags exactly, so a tag-only search is served only when each value is a vocabulary-confirmed tag and a brand has a key some product the copy holds carries, once a full load has keyed every brand; an unconfirmed value is sent live as given, where Product Opener canonicalizes it, and a brand under its live IDs. A page past 10 that such a value keeps off the mirror is refused as `page_out_of_range` naming each value and why in `data.unconfirmed`, and is retryable, with the longest known wait as `retryAfter`, when every value went unconfirmed only because its lookup failed: the same call reaches the mirror once a lookup succeeds, so the refusal must not read as the live path's permanent page-10 bound. The as-of time is read before and after the data and the older one cited, so neither a delta raising it nor a full load lowering it ahead of the rows it rewrites leaves the data older than the time it cites.

**A mirror product read pairs with the mirror's stored sets, and a live one with the live ones.** The as-sold selection for a prepared-only read comes from the same source as the product read, so one answer never mixes two revisions of a record. From the mirror the sets come from the stored record with no request.

**A mirror product read is gated per requested field on the row's record version.** The record builder projects `generic_name` and `nutrient_levels` from record version 2 and `lang`, `ingredients_text_languages`, `nutriscore_score`, `ecoscore_score`, `image_ingredients_url`, and `image_nutrition_url` from version 3, so a row built earlier would answer a full read with those fields silently missing, which `off_get_product` would report as not yet entered. A refresh that finds the last full load built at an older version starts a reload, and the reload rewrites rows over hours, so each read lists the requested fields newer than the row's `record_version` (selected with `doc`, so the gate adds no query; `fieldsNewerThan`). An `off_get_product` read asking for such a field from an older row goes live; a read asking for none of them, a `fields` subset without them included, stays on the mirror throughout the reload. A check on the whole store would send every read live until the reload finished, including reads that need none of the fields and spend the product budget the mirror exists to spare. The fields are named per field rather than per version, so a read requesting `ingredients_text` alone reads live on a row below version 3 (it brings `lang`), while one requesting `nutriments` alone does not. Record dates are no part of this gate: they come from the row's columns, which every row has carried since the store's first version.

**`off_compare_products` serves a predating row as stored and names what it lacks.** Its columns read `nutriscore_score` and `ecoscore_score`, which a row below version 3 lacks, and a compare of up to 10 barcodes that went live for each such row would spend up to 10 product reads of the 15-a-minute budget, for fields that a reload then makes the copy hold, on the call the mirror exists to keep off the upstream. So compare passes `serve_row` (`getProductFields`): the row is served at once, `mirror_fields_unread` on it names the fields, and says no live read was sent and that `off_get_product` reads them for the barcode, and the text's footer adds "unread fields = not read" so an `N/A` is not read as "not entered" when the cell was never read. Scores in the table read `grade (points)`; points without a grade read `N/A (4)`, so neither surface drops them. Nutri-Score points are shown beside the grade but break a tie only between products of one kind, since beverages and fats, oils, nuts, and seeds are graded on their own thresholds and the same points carry different grades across kinds.

**A failed live read over an older row answers from the row, naming the fields it lacks.** On deploy every row is older until the reload completes, hours later on the hosted server, and the release before it answered every full read from those rows with no request. A mandatory live read made each one depend on Open Food Facts and the product budget for the whole window: an outage, a 429, a spent budget, a refusal, or a 404 for a record the copy still holds failed a call that had been answered. So the live read supplies the fields the row predates when it can, and when it raises a declared failure or finds no product the row answers without them, with `mirror_fields_unread` saying they were not read (so their absence is not read as "not entered"), quoting the failure or saying no product was found, and the footer's "not yet entered" narrowing to the rest. A not-found falls back too: the copy still holds the record as of `mirror_as_of`, as it does for a row already rewritten, so the answer does not flip between found and not found as the reload moves through the store. Its not-found note says Open Food Facts may have removed the product at any time since the copy's last full reload (about every 30 days), because only a full reload brings a removal, so `mirror_as_of` does not bound it. The caller's cancellation is rethrown, as is anything that is not a declared failure. A failing read can take its whole 35 s retry deadline before it falls back; the call still settles inside the 55 s chain.

## Known Limitations

- **Crowd-sourced completeness varies widely by region.** French and Western European products are well-covered; products from other regions may be sparse or missing entirely.
- **The live taxonomy cannot be listed or paged.** `search.openfoodfacts.org/autocomplete` suggests against a term: it reports no match total, has no offset or cursor, and answers an empty list for an empty query. So `off_browse_taxonomy` reports no `total_in_facet` for the six live facets, exposes no offset input, and answers an unfiltered call from the in-process sample rather than the full vocabulary (from nothing, for ingredients). The `world.openfoodfacts.org` taxonomy endpoints (`/labels.json`, `/categories.json`) remain 503 for anonymous bots and are unused.
- **E-number terms answer the whole additive vocabulary.** The autocomplete suggester matches display names, so `e322`, `e100`, and `e330` each return all 650 additive tags (live 2026-10-30) rather than the one named. The lookup reads that whole answer and the substring gate picks the tag out (`e314` resolves to `en:e314`, 229th upstream); the chemical name (`lecithin`, `aspartame`, `curcumin`) resolves too.
- **A nutrient constraint reaches only records whose index entry carries the nutrient.** The text index holds nutrient values for part of its records and none for the rest, including records whose live read has nutrition figures (47 of 1,447 `en:skyrs` records carry them in the index, measured 2026-11-24). A product that meets a constraint can be missing from the results, and an empty result does not show that none exists. Bounds compare as the decimals they are, and each row's `indexed_nutriments` shows the index values the constraints were compared against, which can differ from `off_get_product`'s.
- **The stored as-sold read is bounded by the product budget, except from the mirror.** A barcode served by the mirror spends no slot on either read. Each live barcode spends one slot of the 15/min product budget on its product read and a prepared-only one a second on the stored read, and the limiter refuses rather than waits. A 10-barcode compare therefore reads at most 5 stored sets from a fresh minute; the rest end `unread` with reason `rate_limited` and a `retryAfter`, and show only their prepared figures. A record that stores no usable as-sold set (prepared or estimated only, servings under 5 g or ml, units that do not convert) ends `none` with the as-sold fields absent, and a set is served as stored even when the record has its as-sold and prepared sets swapped.
- **The text index date is best-effort.** `text_index_as_of` is absent while the probe has not yet run, within 15 minutes of a failed probe, when fewer than two search slots are free, and after the probe's 3 s timeout, and `text_index_snapshot` then says only that a recently contributed product can be missing. A date is reused for 6 hours, so it can trail the index by that long. Row times on a text search (`last_modified`, `created`, `quantity`, `completeness`) are the indexed revision's, which can be older than the live record's.
- **Brand searches read live until a record-version-4 full load completes.** The mirror keys each brand at ingest, so a store whose last full load was built below version 4 holds some brands under their stored spellings. Deploying version 4 starts a full reload that rewrites every row over hours, and until it completes a tag-only search carrying `brands_tag` reads `/api/v2/search`, which stops at page 10: a page past 10 is answered by one live count, empty with that total when the live matches end before the page, refused as `page_out_of_range` (`data.brand`, `data.live_total`) otherwise. The same applies to a brand the mirror holds no product under, in any of its keys.
- **A live brand search reaches the spellings it can name.** `/api/v2/search` matches the brand as given and, as exact stored tags, each of its keys (`xx:<key>!`), so a record that typed the brand in another case carries a tag neither names: `Красный Октябрь` counts 23 live (live 2026-11-24, 16 for the given value alone) against 28 on a mirror built at version 4, whose key also counts the records typed `Красный октябрь` and `красный октябрь`.
- **Free text reaches names in 31 languages and each record's main language.** The text index holds name fields for 181 languages, and the service sends 31 codes plus `main`, so a product named only in another language than its record's main one, and none of the 31, is found by tag filters rather than by `query`.
- **A stop word of a searched language is not required.** 2.x leaves stop words out of the words a query requires, in every language sent, so a content word that is a stop word in one of them (Spanish `soy`) does not narrow the result. A tag filter is the way to make such a constraint hard (`categories_tag: "en:soy-based-drinks"`).
- **Tag canonicalization resolves English names.** The autocomplete suggests against English display names, so a synonym or singular resolves on the text path only when its English form is a name of the tag; the tag path, served by Product Opener's own canonicalizer, resolves more.
- **A tag-only search read live reaches page 10 at most.** Product Opener serves no deeper page to a client that is not logged in, so at `page_size` 100 a live tag-only search reaches its first 1000 matches; narrowing the filters or changing `sort_by` reaches others, and a search carrying `query`, `nutrient_filters`, or `ingredients_tag` pages through the text index's first 10,000. Only the local mirror lifts the bound, to its first 10,000 results, and only for a search whose every tag value it can match as stored; without `OFF_MIRROR_PATH`, with a mirror not yet loaded, or with a value no vocabulary confirms, the search is live and bounded.
- **The mirror reflects contributor edits as of its last applied delta.** A product contributed or edited since is missing or shown as it was, and a product Open Food Facts removed since the last full load is still served until the next one (up to 30 days). While the export stops regenerating, the mirror stays as of the last delta it can reach without a gap. While a full reload of an export older than the last delta runs, which can take over an hour, `mirror_as_of` drops to the time the rewritten rows reflect, and returns to the last delta's end once the load completes and the deltas past the export re-apply. After an export that builds no product is refused, each refresh downloads it again and applies no delta, so `mirror_as_of` holds until an export that lists products replaces it. A product whose export or delta line was skipped as malformed or oversize is missing or shown as it was until its next edit or the next full load. A record saved before schema 1004 is served with the tags it stores; a live read adds the parents today's taxonomy gives its categories, labels, origins, allergens, traces, and countries, and shows a brand under the brands taxonomy's name. Under the default order, `popularity_key`, and `unique_scans_n`, mirror order follows the values stored with each record and can differ page for page from a live search.
- **The mirror serves a recomputed value late.** Open Food Facts recomputes derived values (Nutri-Score, NOVA group, Green-Score, nutrient levels, estimated nutrients, parsed ingredients and their analysis, additives, allergens and traces, data-quality tags; completeness when it recomputes history) without moving a record's `last_modified_t`, and the daily deltas select records by it, so no delta carries a recompute: the mirror serves the previous value until the record's next edit or the next full load, up to 30 days later, and every `mirror_snapshot` says so. A tag-only search matches those stored values.
- **An exclusion cannot see missing data.** A product with no allergen or trace data entered passes `exclude_allergens` and `exclude_traces`, so an excluded result set is a shortlist to check with `off_get_product`, not a guarantee.
- **Search rate limit is strict (10/min).** Agents running rapid multi-search workflows will hit this. Surface the rate limit in service-layer error messaging and backoff.
- **Barcode collisions exist.** A small number of barcodes map to multiple regional product variants. OFF returns the most-contributed variant; the tool doesn't attempt disambiguation.
- **Eco-Score/Green-Score is often "unknown".** Requires packaging material data, origins, and transport data — typically incomplete. The tool returns the value as-is.
- **A Green-Score filter and a row's Green-Score can disagree.** A tag-only `ecoscore_grade` search matches `environmental_score_tags`, the grade Open Food Facts files for France, while each row shows the world `ecoscore_grade`, so a row can show a letter other than the one it matched.
- **A grade filter on a text search matches the index's grades.** The text index lags the live records, so a row's grade can differ from the one `off_get_product` returns; the row shows the index's grade and `text_index_snapshot` says so. A grade filter never moves a search to the text index, so dropping `query`, `nutrient_filters`, and `ingredients_tag` is what reads current grades.
- **NOVA group 2 (culinary ingredients) is rarely tagged.** Most products without a NOVA tag are either unprocessed (1) or ultra-processed (4); the middle categories are underrepresented in crowd-sourced data.

## API Reference

### Endpoints used

| Endpoint | Method | Local budget |
|:---------|:-------|:-------------|
| `/api/v2/product/{barcode}.json?fields=…` | GET | ~15/min |
| `/api/v3.5/product/{barcode}?fields=nutrition.input_sets` (only for a product read that returned prepared figures and no as-sold one) | GET | ~15/min (product budget; 20 s deadline) |
| `/api/v2/search?fields=…&page=…&page_size=…&{filters}` | GET | ~10/min |
| `search.openfoodfacts.org/search` (JSON body: `q`, `langs`, `fields`, `page`, `page_size`, `sort_by`) | POST | ~10/min (search budget) |
| `search.openfoodfacts.org/search` (the text index date probe: JSON body `sort_by: "-last_modified_t"`, `page_size: 1`, `fields: ["last_modified_t"]`, no `q`; at most one per 6 h, 15 min backoff after a failure, 3 s timeout) | POST | One search slot, taken only while two or more are free |
| `search.openfoodfacts.org/autocomplete?q=…&taxonomy_names=…&size=…` | GET | ~10/min (taxonomy budget) |

Only the first three rows are governed by a published upstream limit. Open Food Facts documents 15 req/min/IP for `GET /api/v*/product` and 10 req/min/IP for `GET /api/v*/search`, both on `world.openfoodfacts.org`; the local budgets match. A text search with tag filters, and a search on either path with exclusions, can also spend taxonomy-budget requests: one per tag or exclusion value the offline sample does not confirm and no earlier search has resolved. `search.openfoodfacts.org` is a separate deployment (search-a-licious) that the published limits do not name and for which no limit is documented, so its two rows are conservative local choices, not mirrors of an upstream figure. The text and tag search paths share one budget, so requests reaching the endpoint the documented 10/min covers stay within it regardless of how a query routes. The date probe draws on that budget only while two slots are free, so it never takes the last one, and each probe it sends (at most one per 6 hours, or per 15 minutes while it keeps failing) counts against it. A tag-only search past page 10 for a brand the mirror cannot match spends one `/api/v2/search` slot on a count (`page_size` 1).

### Field selection

All requests must include `fields=`. Without it, the response is ~200 keys and 50–200KB per product. Minimal field sets:

- Product summary: `product_name,brands,nutriscore_grade,nova_group`
- Full label: `PRODUCT_FIELD_NAMES` (`src/services/openfoodfacts/types.ts`), from `product_name` through `created_t`, including `lang`, `ingredients_text_languages`, `nutriscore_score`, `ecoscore_score`, `image_ingredients_url`, `image_nutrition_url`, `last_modified_t`, and `created_t`

### Search filter parameter names

| Filter | Parameter name | Format |
|:-------|:---------------|:-------|
| Category | `categories_tags` | `en:breakfast-cereals` |
| Category (English slug) | `categories_tags_en` | `breakfast-cereals` |
| Brand | `brands_tags` | `nutella`; the brand as given, then each key as an exact stored tag: `Красный Октябрь\|xx:красный-октябрь!` |
| Label | `labels_tags` | `en:organic`, or `en:organic,en:fair-trade` for both |
| Nutrition grade | `nutrition_grades_tags` | `a`, or `a\|b` for either |
| NOVA group | `nova_groups_tags` | `4`, or `1\|2` for either |
| Green-Score grade | `environmental_score_tags` | `a-plus`, or `a\|a-plus` for either |
| Country | `countries_tags` | `en:france` |
| Allergen | `allergens_tags` | `en:milk`; `-en:milk` excludes; `en:nuts,-en:milk` combines |
| Trace ("may contain") | `traces_tags` | `en:nuts`; `-en:nuts` excludes |
| Ingredient analysis verdict | `ingredients_analysis_tags` | `en:vegan` |
| Additive | `additives_tags` | `en:e322` |

A `*_tags` value is a comma-separated AND list, a `-` prefix negates an entry, and a `|`-separated value is any of its entries.

### Text search field names

The text path (`POST https://search.openfoodfacts.org/search`) names the same filters by search-a-licious 2.x's fields, which refuse an unknown field with HTTP 400. Clauses are ANDed into `q`; a value sent under several IDs is one quoted any-of group.

| Filter | `q` field | Format |
|:-------|:----------|:-------|
| Category | `categories` | `"en:breakfast-cereals"` |
| Brand | `brands` | `("xx:<given>" OR "<key>" OR "xx:<key>" …)` |
| Label (each value its own clause) | `labels` | `"en:organic"` |
| Allergen | `allergens` | `"en:milk"`; `-allergens:"en:milk"` excludes |
| Trace ("may contain") | `traces` | `"en:nuts"`; `-traces:"en:nuts"` excludes |
| Additive | `additives` | `"en:e330"` |
| Country | `countries` | `"en:france"` |
| Ingredient (each value its own clause) | `ingredients_tags` | `"en:inulin"` |
| Ingredient analysis verdict | `ingredients_analysis_tags` | `"en:vegan"` |
| Nutri-Score grade | `nutriscore_grade` | `a`, or `(a OR b)` for either |
| NOVA group | `nova_group` | `4`, or `(3 OR 4)` for either |
| Green-Score grade | `environmental_score_grade` | `a`, `"a-plus"`, or `("a-plus" OR a)` for either |
| Nutrient (per 100 g, or per 100 ml) | `nutriments.<nutrient>_100g` | `[* TO 2]`, `{* TO 2}`, `{3.5 TO *}`, `[3.5 TO *]`, each bound as given |
| Query | bare words, last | lowercased, escaped, space-joined |

Rows come back from `fields` = `TEXT_SEARCH_RESULT_FIELDS`: `categories` is the row's `categories_tags`, `environmental_score_grade` its `ecoscore_grade`, and `brands` (tag IDs) its `brands` with the leading `xx:` dropped. `langs` is the 31 codes and `main`.

### Response envelope

```json
{
  "count": 25894,
  "page": 1,
  "page_count": 5,
  "page_size": 5,
  "skip": 0,
  "products": []
}
```

`page_count` = products on this page (equals `page_size` on full pages, less on the last). Total pages = `Math.ceil(count / page_size)`. Pagination uses `page` (1-based) + `page_size`. No cursor tokens.
